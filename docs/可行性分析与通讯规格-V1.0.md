## 1. 可行性结论

**可以实现。** 核心链路「操作员按仪器保存按钮 → App 自动获得结果并入库」在厂家协议下**成立**，但有两个前提：

1. **必须用「单次 Modbus 请求连续读 0x1C~0x1E」**（见 §5.2），把 0x1C 清零与 0x1D/0x1E 取值放进同一个仪器响应快照，从协议层面消除主要丢失窗口 —— 厂家示例文档明确允许一次读取（可读全部寄存器）。
2. **0x1C 在仪器无上位机连接期间的行为未经厂家证实**【待确认#4】，若仪器仅保留"最新一笔"且 App 离线期间发生多次保存，中间结果会丢（仪器侧物理限制，App 无法完全弥补，需现场实测明确风险边界，见 §7）。

其余（自动轮询、重连、本地库、导出）均为成熟技术，无不可逾越障碍。

## 2. 厂家协议事实总结（两份 PDF 核对结果）

### 2.1 MODBUS-RTU（RS485）【事实】

| 项目 | 值 |
|---|---|
| 接口 | RS485 标准 |
| 帧格式 | N-8-1，无校验，8 数据位 1 停止位，波特率 115200 |
| 设备地址 | 默认 0x01 |
| 功能码 | 0x03 读保持寄存器 / 0x06 写单寄存器 / 0x10 写多寄存器 |
| 前置条件 | 测温仪系统参数 [通讯接口] 设为"通讯" |

> 本项目走 Wi-Fi，RTU 仅作协议理解背景，**不使用**。

### 2.2 MODBUS-TCP/IP（191AF+，本项目实际使用的通道）【事实】

- 仅 **191AF+** 支持（需硬件支持无线通讯）；2.4G Wi-Fi。
- 报文格式：`MBAP Header | Function Code | Data`（注意：MODBUS TCP **没有 RTU 的 CRC**，也没有从机地址字段，从机地址被 MBAP 的 Unit ID 取代）。
- 前置：测温仪系统参数 [无线协议] 设为 **MB-TCP**；用**扫码**配置本机静态 IP 与端口，默认端口 **502**。
- **上位机是客户端**：网络连接成功后由上位机（平板）主动发请求，仪器被动应答。**仪器不会主动推送**。
- 巡检建议 **≈1 秒**；**发送间隔 >60s 仪器将认为通讯超时**。
- 仪器寄存器表在 TCP 与 RTU 下相同（地址分配参考同一章节）。

### 2.3 扫码配置指令【事实】

通用指令（测试对象工艺参数，存进仪器，随后可经寄存器读出）：

| 参数 | 指令 | 示例 |
|---|---|---|
| 设备信息(SN) | `SN=` | `SN=QK-HT-001` |
| 设定温度 | `TSET=` | `TSET=350` |
| 误差范围 | `TERR=` | `TERR=20` |

无线网络指令（191AF+）：`WifiName=` / `WifiPassword=` / `ServerIP=` / `ServerPort=` / `GateWay=`（**MB-TCP 模式下才配置 GateWay**）。多条用**英文逗号**组合成一个二维码。

**【关键事实】ServerIP 的含义随协议而变**：
- MQTT 模式：ServerIP = 上位机 IP（仪器 IP 由路由器 DHCP 分配）
- **MB-TCP 模式：ServerIP = 仪器自己的固定 IP**（示例文档原文："备注：ServerIP=192.168.170.104 为测试仪的固定 IP 地址（用户指定）"）

> ⚠️ 示例文档中 TCP 示例的二维码写的是 `ServerPort=1883`，与"默认端口 502"矛盾 —— 疑似从 MQTT 示例复制遗漏【未知/待确认#15】。本项目 App 作为客户端连仪器，端口在 App 配置里填（默认 502），与仪器实际配置保持一致即可，不受该示例错误影响。

## 3. 寄存器分析（保持寄存器，191AF/191AF+ 通用）【事实】

寄存器总数 **31 个（0x1F）**，地址 0x00~0x1E【事实：通讯示例文档"寄存器总数为 001FH"】。全部按**大端序**传输（高字节在前）【事实：示例 00EA=234】。通用写功能码 0x06（写单寄存器）。

| 地址 | 名称 | 类型/示例 | 单位/缩放 | R/W | App 用途 |
|---|---|---|---|---|---|
| 0x00 | 实时温度 | 数值，例 00EA=234 | ℃，**系数 0.1** → 23.4℃ | R | 测量页大屏显示 |
| 0x01 | 温度单位 | 0=℃，1=℉ | — | R/W | 显示换算前提【未知#5】 |
| 0x02 | 结果保存 | 0=手动，1=自动 | — | R/W | 可配置项（默认不写）【未知#6】 |
| 0x03 | 自动关机时间 | 0/5/10/15 分钟 | 分钟 | R/W | 可配置项（默认不写） |
| 0x04~0x09 | 备用 | — | — | — | 不读不写 |
| 0x0A~0x19 | 设备信息(扫码) | 字符串，按字节解析，16 寄存器=32 字节 | ASCII【推断，编码未知#2】 | R | 记录"设备SN"字段 |
| 0x1A | 设定温度(扫码) | 例 350 | ℃，**系数 1**（整数） | R | 记录"设定温度" |
| 0x1B | 误差范围(扫码) | 例 10=±10℃ | ℃，系数 1 | R | 记录"误差范围" |
| 0x1C | 测试上传标志 | 0=无效，1=保存按钮按下；**读取后自动清零** | — | R | 新结果检测（核心） |
| 0x1D | 测试保存温度 | 例 351 | ℃，**系数 1**（整数） | R | 记录"测量温度" |
| 0x1E | 测试合格判定 | 0=NG，1=OK | — | R | 记录"结果" |

**必须重点区分两条缩放规则【事实】**：
- `0x00` 实时温度：**系数 0.1**（寄存器值 ×0.1）
- `0x1A / 0x1B / 0x1D`：**系数 1**，寄存器值即整数 ℃（示例 350/10/351 均不带小数）

**解读**：0x1A/0x1B 是"测试对象工艺参数"（扫码 TSET/TERR 的镜像），0x0A~0x19 是扫码 SN 的镜像（"设备信息（扫码）"）【推断：三者的"（扫码）"标注 + 扫码指令 SN/TSET/TERR 名称一一对应】。0x1C~0x1E 是每笔测试结果通道。

【未知/待确认】详见 §12：#2 SN 字符串编码与最大长度；#5 单位切换是否影响 0x00/0x1D 数值（若 0x01=1 时 0x00 变 ℉，App 需按 0x01 解释）；#6 0x02"自动保存"的确切行为（自动模式下是否无需按保存钮即产生 0x1C=1？—— 若是，现场可设为自动，App 将完全无人值守，但需仪器实测确认）；#7 0x03 与 0x1C 的交互；#9 0x1D 是否可能带小数（TSET 若支持 0.5℃ 级工艺参数）。

## 4. MODBUS TCP 报文设计（字节级）

### 4.1 MBAP 头结构【事实 + 通用标准】

上位机→仪器（每帧）：

```
| 事务ID(2B) | 协议ID(2B) | 长度(2B) | 单元ID(1B) | PDU... |
  0001         0000        0006       01
```

| 字段 | 长度 | 取值 | 说明 |
|---|---|---|---|
| Transaction ID | 2B | 自增（例 0x0001） | 请求响应回显配对；**必须用 16 位自增计数，同一时刻在途请求必须配对等待**（响应中回显） |
| Protocol ID | 2B | 恒 0x0000 | MODBUS TCP 固定 |
| Length | 2B | 0x0006 | = 单元ID(1) + PDU 长度(5)；不含 MBAP 本身 |
| Unit ID | 1B | 0x01（可配） | 对应 RTU 从机地址概念，仪器忽略/校验未知【未知#10】 |

### 4.2 App 的实际轮询请求 —— 【推断】+【事实】

**方案：每个巡检周期发 1 个请求，一次读全部 31 个寄存器（0x00 起 0x1F 个）**：

```
TX: 00 01 00 00 00 06 01 03 00 00 00 1F
    ─── ─── ─── ─── ─── ── ── ───── ─────
     │   │    │    │   │   │  │    │    └─ Quantity=0x001F (31)
     │   │    │    │   │   │  │    └─ Start Address=0x0000
     │   │    │    │   │   │  └─ FC=0x03 读保持寄存器
     │   │    │    │   │   └─ Unit ID=0x01
     │   │    │    │   └─ Length=0x0006
     │   │    │    └─ Protocol ID=0x0000
     │   │    └─ Transaction ID=0x0001(低字节)
     └─ Transaction ID=0x0000(高字节)
```

```
RX: 00 01 00 00 00 43 01 03 3E <62字节寄存器数据...>
    长度=0x0043=67 = 1(UnitID)+1(FC)+1(字节数)+62(31×2)
```

一次全读的**依据**：
1. 示例文档明示"可以一次性读取全部数据，寄存器总数为 001FH"【事实】；
2. 结果快照一致性：0x1C（标志）+0x1D（温度）+0x1E（判定）+0x00（实时温度）+0x1A/0x1B（工艺参数）出自**同一响应**，时间戳完全对齐，消除多次请求间的仪器状态漂移；
3. 0x1C"读取后自动清零"若以仪器**完成一次读命令处理**为动作点【推断，见 §5.2】，则标志、温度、判定同帧取得后清零，丢失窗口最小化；
4. 流量：每轮 1 请求/响应 ≈ 150B，1s 周期完全无压力，不会导致仪器通讯超时。

> 备选方案：读 0x1C~0x1E（3 寄存器）短帧，理由同上但窗口无区别、且拿不到同快照的 0x00/0x1A/0x1B。**不采用**，全读更优。
> 设备信息 0x0A~0x19 随全读自然带回（32 字节），App 记录设备 SN 无需额外请求。

### 4.3 异常与边界

- 仪器异常应答：`FC | 0x80` + 异常码（例 `83 01`=非法功能）。TCP 下无 CRC 校验【事实】，靠 Length 字段与帧结构校验。
- 响应 Length 与实际字节数不符 / 事务 ID 不匹配 → 丢弃、判超时重试【推断，属标准实现】。
- 仪器支持的最大 Quantity 无文档说明；31 < 125 标准上限，无风险【事实：全表仅 31 寄存器】。

## 5. 自动获取结果流程与可靠性分析

### 5.1 目标流程【事实 + 需求】

```
操作员测量 → 按仪器保存按钮 → 仪器：0x1C=1, 0x1D=保存温度, 0x1E=OK/NG
   ↑                                                        ↓
App 1s 轮询一次，读到 0x1C=1 → 本帧内即含 0x1D/0x1E → 写入本地库 → UI 弹结果
```

### 5.2 为什么必须一次读 0x1C~0x1E（同帧全读）【推断，需测试 C/D/E 验证】

假设分两次请求：先读 0x1C 返回 1，随后仪器清零；第二次读 0x1D 前 App 崩溃或网络中断 → **0x1D/0x1E 未取到且 0x1C 已清，该笔数据永久丢失**。这是协议层面最大的丢失窗口。

同帧全读后，仪器对**一个**读请求产生响应快照，0x1C=1 与 0x1D/0x1E 从同一快照解析：
- 若仪器清零发生在"响应发送时"→ 快照内三个值完整有效，App 拿到即安全；
- 若仪器清零发生在"请求到达时"（先清再快照）→ 0x1C 将读回 0，本笔**漏检但未丢**（App 下轮无感知，数据仍悬在仪器上直到下一次保存覆盖）—— 此行为**必须实测确认**（测试 C：按保存后立即读；测试 D：连续两次读看是否 0x1C 先 1 后 0 但 0x1D/0x1E 同帧有效）。

**App 侧防护**：确认点 =「收到含 0x1C=1 的响应」即事务开始，DB 写入成功即事务结束，中间不退出（见 §6 状态机）；崩溃重启后通过 pending 恢复（若 pending 内容 = 上帧快照，重试插库）。

### 5.3 可靠性边界（必须对用户/厂家讲清楚）【推断 + 未知】

| 场景 | 行为 | 结论 |
|---|---|---|
| App 连接中，操作员连续快速保存两笔 | 0x1C 是单寄存器"最新一笔"【推断】；1s 周期内若两笔都落定 → 第二笔覆盖第一笔标记，第一笔仅当 0x1D 仍指向最新一笔才可读 | 高风险【未知#7 需确认两笔最小间隔与覆盖行为】 |
| App 离线（Wi-Fi 断/仪器关机），期间按保存 | 若仪器保留标志等待上位机读取 → App 恢复后补收（不丢）；若仪器重启清 0x1C → 丢 | 无法保证【未知#4 需实测测试 G】 |
| 读 0x1C=1 帧已收到、DB 写前 App 崩溃 | 下轮重读，0x1C 已清 → 该帧数据已随崩溃丢失（毫秒级窗口） | 防护：读帧→立即插库在同一协程内完成；崩溃只发生在极端情形【推断：窗口极小但存在，测试 E 观察】 |

> **结论：协议本身没有"每笔独立编号/历史缓冲"能力【推断：0x1C~0x1E 只描述最新一笔，未发现历史缓冲寄存器】，所以「操作员按保存」与「App 入库」之间只要存在间隙就有理论丢失可能。App 能把窗口压缩到~毫秒，但**若现场要求 100% 不丢，必须请厂家确认**：(a) 0x1C 是否在无连接时保持=1 并保留 0x1D/0x1E；(b) 连续保存两笔的最小间隔；(c) 是否存在未公开的历史/批寄存器（例 0x1F 之后或功能码扩展）。**

## 6. 状态机设计

单连接单事务，全程**一个专用轮询协程**顺序执行（无并发读写仪器），状态对外以 StateFlow 暴露。

```
         ┌───────────────────────────────┐ 掉线/异常
         ▼                               │
    DISCONNECTED ──connect()──▶ CONNECTING ──socket ok──▶ CONNECTED
         ▲                                  │                  │
         │            connect 失败/超时      ▼                  ▼
         └──────────── RE-CONNECTING ◀── NETWORK_ERROR ◀── POLLING
                              │  (指数退避: 1s,2s,4s...30s 封顶)   │
                              └─────── 成功 ─────────────────────┘
   POLLING（每 pollInterval 一次，默认 1000ms）
      │  readAll(0x00, 0x1F)
      ├─ 响应 OK 且 0x1C=0 → 更新实时温度/工艺参数 → 回 POLLING（下一拍）
      ├─ 响应 OK 且 0x1C=1 ─▶ RESULT_READY（快照已含 0x1D/0x1E，挂起后续轮询）
      │        │
      │        ├─ DB 事务写入成功 ─▶ 幂等键登记 ─▶ UI 广播结果 ─▶ 回 POLLING
      │        └─ DB 写入失败 ─▶ 本地重试(3次) ──仍失败──▶ 标记 ERROR + 界面告警
      │                                                  （数据保留在内存快照，不静默丢弃）
      └─ 超时/IO 异常/异常响应 ─▶ NETWORK_ERROR（连读失败计次；连续 N 次判定断线→DISCONNECTED）
```

| 状态 | 进入条件 | 行为 |
|---|---|---|
| DISCONNECTED | 启动/用户停止/断线确认 | 空闲，不占 socket |
| CONNECTING | 用户启动或自动重连 | TCP 连接 + 首帧试探读；超时 = socketTimeout(默认 2s) |
| CONNECTED | socket 建立 | 立即转入 POLLING |
| POLLING | 每周期 | 执行全读；本帧无新结果则**不回写任何寄存器** |
| RESULT_READY | 0x1C=1 | 暂停轮询直至入库完成（防并发重入） |
| NETWORK_ERROR | 读超时/IO | 关闭 socket → RE-CONNECTING（退避） |
| ERROR（数据面） | 入库失败重试耗尽 | UI 红色告警条，保留快照等待手动重试 |

**防重复保存**：每次 RESULT_READY 生成 `snapshotId = hash(时间戳+0x1D值+0x1E值)`，写入前查本地库是否已存在同 ID（唯一索引冲突忽略）；DB 事务内完成"插入 + 标记"，天然幂等。由于快照来自仪器清零前唯一一帧，同一帧不可能被解析两次（0x1C 已清），幂等键是双保险而非主机制。

**生命周期**：轮询协程挂在前台服务（见 §10.3）；Activity 销毁不停止采集；App 冷启动先读本地配置再自动连。

## 7. 数据丢失风险专项分析（Prompt §32 的逐条回答）

| 问题 | 回答 |
|---|---|
| App 读 0x1C 后清零、读 0x1D 前崩溃，会丢吗？ | **存在该风险（分帧读取设计下）**。本设计用**同帧全读**规避：0x1D/0x1E 与 0x1C 在同一响应内到达，不存在"已清零但未取数据"的中间态【推断：依赖仪器"响应快照式清零"，需实测】 |
| 是否一次请求读 0x1C~0x1E？ | 是 —— 并进一步一次全读（§4.2），同快照还含 0x00/0x1A/0x1B |
| 是否先读 0x1D/0x1E 再读 0x1C？ | 无意义：0x1D/0x1E"0x1C=1 时有效"，先读可能读到上一笔残留；快照式读法才自洽 |
| 如何减少失败窗口？ | 单协程串行 + 收到帧立即入库 + 入库失败重试保留内存快照 + 前台服务保活（防进程被杀） |
| 是否需要本地 pending 状态？ | 需要（Room 表 pending_results，崩溃恢复后若 0x1C 已清但 DB 无记录，用 pending 补记 —— 实测确认 0x1C 行为后再定级） |
| 必须厂家确认的问题 | #4（离线保存滞留）、#7（连续保存间隔/覆盖）、#8（是否有一笔=寄存器只读后清零的全流程）、#13（是否存在更多结果寄存器） |

```

│  UI Layer (Compose)                                                     │
│    测量页 / 历史页 / 配置页 / 线别机种管理页                               │
```

- **ModbusTcpClient**（独立模块，不依赖 Android 框架）：`connect/disconnect/readRegisters(addr,qty)/writeRegister` + 帧编解码 + 事务 ID 配对 + 超时。**自实现，不用第三方库**（理由 §13）。

- Room 与配置 JSON 分离（§10.2），与 UI 完全解耦。
- 单 Activity + Compose 导航；页面间仅共享 Repository 层单例。

## 9. 数据库设计（Room + SQLite）

**评估**：本项目 4 张表、DAO 间关联与组合筛选多，Room 提供编译期 SQL 校验、Flow 响应式查询、事务注解，且 **Room 就是 SQLite 的封装**（同一存储文件，无多余依赖成本）→ **采用 Room 2.6.1 + KSP**。若未来构建链出问题，回退方案为旧项目验证过的裸 SQLiteOpenHelper（表结构不变，DAO 换手写 SQL）。

```sql
Line(id PK, name UNIQUE NOT NULL, enabled, createdAt, updatedAt)
Model(id PK, name UNIQUE NOT NULL, enabled, createdAt, updatedAt)
DeviceConfig(id=1 单行, name, ip, port, unitId, pollIntervalMs, timeoutMs, enabled)
MeasurementRecord(
  id PK AUTOINCREMENT,
  snapshotId UNIQUE,          -- 幂等键 (§6)
  timestampMs,
  lineName, modelName,        -- 冗余快照：线别/机种改名或删除不影响历史溯源
  deviceId(SN 字符串, 仪器0x0A~0x19), deviceIp,
  setTemperature,             -- 0x1A (整数 ℃)
  measuredTemperature,        -- 0x1D (整数 ℃)；0x00 仅实时显示不落历史
  tolerance,                  -- 0x1B (±℃)
  result,                     -- OK / NG（由 0x1E 判定，App 不自行判定【事实】）
  rawHex?（调试期可选，正式版移除）
)
ConfigMeta(key PK, value)     -- 上次选中线别/机种、导出路径等界面态
```

**取舍说明**：历史记录不存外键，只存线别/机种**名称快照** —— 工厂场景线别机种被删改后历史报表必须仍可溯源；筛选用名称 + 时间索引。查询筛选（日期区间/线别/机种/OK NG/关键词）走 DAO 组合查询，Flow 驱动历史页实时刷新。

## 10. 配置文件方案

**分析结论：Room 即配置真源（单写单读），JSON 文件仅作"配置包"导入/导出载体**，不做双写同步 —— 双写会产生一致性难题，违背"配置文件不能影响数据库存储"的要求。

- 导出：线别表 + 机种表 + 设备配置（含上次选中态）→ 序列化 JSON → `配置备份_yyyyMMdd.json`（系统分享/拷贝）。
- 导入：读 JSON → 事务内 upsert（名称冲突策略：默认"跳过并列出冲突"，提供"覆盖"选项）→ **绝不触碰 MeasurementRecord**。
- 密码类字段（仪器 WiFi 密码）不在此方案范围（那是 191AF+ 侧扫码配置的内容）；App 侧不需要存 WiFi 密码。

**复刻到另一台平板**：新平板装 App → 配置页导入 JSON → 完成（含仪器 IP 等）【推断：可满足 Prompt §14 需求】。

## 11. Excel 导出方案（评估与选择）

| 方案 | 评估 |
|---|---|
| Apache POI | Android 上体积 ~10MB+、dex 方法数压力大、官方不支持 Android（需移植版）、慢。**否** |
| FastExcel | 内存友好写入快，但 Android 支持与版本长期维护存疑，且本项目数据量级（单班次几百~几千行）用不上它的性能优势。**否** |
| **手写最小 XLSX（ZipOutputStream + sheet XML，内联字符串）** | **采用。** xlsx 本质是 zip 包 + XML；仅固定表头 + 数值/文本单元格的报表几十行代码即可生成合法文件。**旧项目 Quick192AF-App 已用此方案现场验证可被 Excel/WPS 正常打开**，零新增依赖、无版本风险 |

导出入口在历史页：当前筛选结果 → `测量记录_yyyyMMdd_HHmm.xlsx`，列 = ID/时间/线别/机种/设备/设备IP/设定温度/测量温度/误差范围/结果（日期与温度按用户显示习惯格式化）。导出前可选：日期区间、线别、机种、结果过滤（复用历史页筛选条件）。行数超过 Excel 单表上限（104 万行）时按日期分 sheet —— 实际不可能触发，作防御处理。

## 13. 通信模块：自实现 vs 第三方库

| 方案 | 评估 |
|---|---|
| jlibmodbus / modbus4j | PC 向库，Android 兼容与维护一般；现代 modbus 库活跃度普遍低 |
| **自实现（java.net.Socket + 帧编解码）** | **采用。** 本项目协议面极窄（仅 FC03 读全表 + 可选 FC06 写单寄存器，TCP 无 CRC），自实现 <200 行，可完整控制超时/重连/日志；旧项目 net/Modbus.kt 已验证自研编解码路径；无第三方依赖 = 无供应链与版本风险，符合工业长期维护原则 |

关键实现点：同步阻塞 IO + 独立协程（Dispatchers.IO）；SO_TIMEOUT = timeoutMs；事务 ID 16 位自增；每响应校验 MBAP 长度与回显；协议级超时计次驱动断线判定。

## 14. 网络异常处理设计（Prompt §20/§31 覆盖）

| 场景 | 处理 |
|---|---|
| 仪器断连/关机 | 连续 2 次读失败 → 判定断线 → 关闭 socket → 指数退避重连(1,2,4…30s 封顶)，UI 显示"重连中 (第n次)" |
| Wi-Fi 断开（平板侧） | ConnectivityManager 网络回调触发；无网时暂停重连协程，恢复后立即重连 —— 补上 Android 13+ 网络状态查询限制的兼容写法 |
| App 退后台 | 采集在前台服务（CollectionService，前台通知"测量收集中"），轮询不中断；**数据不因界面销毁而丢** |
| 屏幕休眠（平板无人值守） | 前台服务持 PARTIAL_WAKE_LOCK + 测量页 FLAG_KEEP_SCREEN_ON（可配置）—— 保证 TCP 长连接不被 CPU 休眠掐断；Wi-Fi 睡眠策略设"始终连接"【推断：系统级，App 内申请 Wi-Fi lock 兼容】 |
| 解析错误 / 异常响应 | 计次跳过本帧，不崩溃；连续异常按断线处理 |
| 恢复后补收 | 若 0x1C 仍=1 → 正常流程补收（前提仪器保留标志，见 §5.3 边界） |

## 15. 通信验证方案（Phase 2 工具功能 ← 映射 Prompt §8 测试 A~G）

Phase 2 交付最小验证 App（独立模块/独立 APK，不进正式包），界面：连接参数输入 + 6 寄存器实时读数面板 + 原始帧 hex 日志 + 自动 1s 轮询开关。日志行如：
```
[22:31:01] CONNECT 192.168.1.100:502 OK
[22:31:02] TX 0001 0000 0006 01 03 0000 001F
[22:31:02] RX 0001 0000 0043 01 03 3E ...  0x00=3526(0.1→352.6℃) 0x1A=350 0x1B=10 0x1C=0
[22:31:03] RX ... 0x1C=1 0x1D=351 0x1E=1  → 一次快照已含全部字段
```
| 测试 | 目的 | 通过标准 |
|---|---|---|
| A 连接后静置读 | 基线值域 | 记录 0x1C~0x1E 初始值 |
| B 不测量持续读 | 0x1C 空闲稳定 | 长时间保持 0 |
| C 保存后立即读 | 触发时序 | 0x1C=1 且同帧 0x1D/0x1E 有效 |
| D 连读两次 | **清零时机（设计生死线）** | 第 1 帧 1/温度/判定齐，第 2 帧 0x1C=0 → 证实快照语义 |
| E 连续两次保存 | 是否丢/覆盖 | 两笔都能在"自动清零前"被读到 |
| F 轮询中随机按保存 | 自动发现 | 无需任何操作 1~2 帧内发现 |
| G 离线期保存→恢复 | 滞留还是丢失 | 若 0x1C 滞留=1 → 补收成功（可靠）；若清空 → 向厂家反馈并重新评估 §7 风险等级 |
| 附测 | 全读(31)与分读(3)行为差异 | 观察清零语义是否一致 → 确定正式版请求方式 |

**测试 D/G 的结论直接决定正式版的两处设计**：请求粒度（§4.2）与 pending 机制（§7）。工具同时输出供厂家追查的复现日志。

## 16. 厂家确认问题清单（可直接发送）

**A. 结果通道与数据安全（最高优先）**
1. 191AF+ 是否确定支持 MODBUS-TCP（MB-TCP），固件版本要求？（我们按 V1.1 软件版本设计）
2. 读取 0x1C 的"自动清零"动作发生在何时：请求到达即清，还是响应发出后清？一次读 0x1C~0x1E 三个寄存器的请求，0x1D/0x1E 是否为同一时刻快照？
3. 上位机未连接期间操作员按保存：0x1C/0x1D/0x1E 会一直保留到被读取吗？中途再次按保存会怎样（覆盖 or 丢弃前一笔）？
4. 连续两次保存之间的最短间隔是多少？会不会丢？
5. 是否存在其它测试结果/历史记录相关寄存器（例如记录序号、缓冲）？完整寄存器表是否只有 31 个（0x00~0x1E）？
6. 0x02"结果保存"=自动(1)时行为是什么：测量完成自动产生 0x1C=1 且无需按保存？自动模式下 0x1D 判定由谁触发？
7. 0x1D 是否始终为整数℃？TSET 扫码是否支持小数（如 350.5）？
8. 0x01 单位=℉ 时，0x00/0x1D 的数值是否也变为 ℉ 表示？

**B. 网络与连接**
9. MB-TCP 模式下仪器 IP 是否必须静态（由扫码 ServerIP 指定）？支持 DHCP 吗？
10. 默认端口 502 与通讯示例中 `ServerPort=1883` 矛盾，以哪个为准？
11. MODBUS TCP 是否只允许一个客户端同时连接？第二个客户端连接或连接被占时会怎样？
12. 超过 60s 无请求"通讯超时"后，仪器是否关闭 TCP？恢复连接需要重新握手吗？
13. 通讯超时或断电后重新上电，Wi-Fi/静态 IP 配置是否保留？
14. Wi-Fi 是否仅 2.4GHz？是否支持 802.11b/g/n 任一种？企业网 WPA2-Enterprise 是否支持（还是仅个人 WPA2/WPA3？）
15. 仪器是否有省电/休眠模式会断开 Wi-Fi？自动关机(0x03)生效时 TCP 连接是否随之断开？
16. GateWay 在 MB-TCP 下的作用？（静态 IP 场景通常需要网关，是否必须配置一致才能通信）

**C. 寄存器与数值**
17. 0x0A~0x19"设备信息(扫码)"：是否即 SN= 指令内容？编码是 ASCII 吗？最大长度？
18. 0x1A 设定温度 / 0x1B 误差范围在按保存那一刻是否可能变化（操作员中途改 TSET 的时序影响）？
19. 0x1E OK/NG 判定是否完全由仪器完成？判定规则与 0x1B 误差范围的关系？（App 只记录不判定）
20. 实时温度 0x00 的刷新率？测量结束、未按保存时 0x00 显示的是什么值（锁存 or 回落）？
