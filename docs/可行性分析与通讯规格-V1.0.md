## 1. 可行性结论

**可以实现。** 核心链路「操作员按仪器保存按钮 → App 自动获得结果并入库」在厂家协议下**成立**，但有两个前提：

1. **必须用「单次 Modbus 请求连续读 0x1C~0x1E」**（见 §5.2），把 0x1C 清零与 0x1D/0x1E 取值放进同一个仪器响应快照，从协议层面消除主要丢失窗口 —— 厂家示例文档明确允许一次读取（可读全部寄存器）。
2. **0x1C 在仪器无上位机连接期间的行为未经厂家证实**【待确认#4】，若仪器仅保留"最新一笔"且 App 离线期间发生多次保存，中间结果会丢（仪器侧物理限制，App 无法完全弥补，需现场实测明确风险边界，见 §7）。

其余（自动轮询、重连、本地库、导出）均为成熟技术，无不可逾越障碍。

## 2. 厂家协议事实总结（两份 PDF 核对结果）

### 2.1 MODBUS-RTU（RS485）【事实】

| 项目 | 值 |
|---|---|
| 接口 | RS485 标准 |
| 帧格式 | N-8-1，无校验，8 数据位 1 停止位，波特率 115200 |
| 设备地址 | 默认 0x01 |
| 功能码 | 0x03 读保持寄存器 / 0x06 写单寄存器 / 0x10 写多寄存器 |
| 前置条件 | 测温仪系统参数 [通讯接口] 设为"通讯" |

> 本项目走 Wi-Fi，RTU 仅作协议理解背景，**不使用**。

### 2.2 MODBUS-TCP/IP（191AF+，本项目实际使用的通道）【事实】

- 仅 **191AF+** 支持（需硬件支持无线通讯）；2.4G Wi-Fi。
- 报文格式：`MBAP Header | Function Code | Data`（注意：MODBUS TCP **没有 RTU 的 CRC**，也没有从机地址字段，从机地址被 MBAP 的 Unit ID 取代）。
- 前置：测温仪系统参数 [无线协议] 设为 **MB-TCP**；用**扫码**配置本机静态 IP 与端口，默认端口 **502**。
- **上位机是客户端**：网络连接成功后由上位机（平板）主动发请求，仪器被动应答。**仪器不会主动推送**。
- 巡检建议 **≈1 秒**；**发送间隔 >60s 仪器将认为通讯超时**。
- 仪器寄存器表在 TCP 与 RTU 下相同（地址分配参考同一章节）。

### 2.3 扫码配置指令【事实】

通用指令（测试对象工艺参数，存进仪器，随后可经寄存器读出）：

| 参数 | 指令 | 示例 |
|---|---|---|
| 设备信息(SN) | `SN=` | `SN=QK-HT-001` |
| 设定温度 | `TSET=` | `TSET=350` |
| 温度上限 / 温度下限 | `TMAX=` / `TMIN=` | `TMAX=360` / `TMIN=340` |
| 漏电压上限 | `VMAX=` | `VMAX=2` |
| 接地电阻上限 | `RMAX=` | `RMAX=2` |

> ⚠️ **2026-09-21 修订**：本表原为厂家文本协议 V1.1 的旧版指令（`SN`/`TSET`/**`TERR`**）。
> 该文档的通用指令表与它的地址表一样是**旧固件版**；现按厂家新版《扫码配置指令》表 1 更新为上表（`TERR` 已删除）。
> 判断依据与单位口径见 **§23**。

无线网络指令（191AF+）：`WifiName=` / `WifiPassword=` / `ServerIP=` / `ServerPort=` / `GateWay=`（**MB-TCP 模式下才配置 GateWay**）。多条用**英文逗号**组合成一个二维码。

**【关键事实】ServerIP 的含义随协议而变**：
- MQTT 模式：ServerIP = 上位机 IP（仪器 IP 由路由器 DHCP 分配）
- **MB-TCP 模式：ServerIP = 仪器自己的固定 IP**（示例文档原文："备注：ServerIP=192.168.170.104 为测试仪的固定 IP 地址（用户指定）"）

> ⚠️ 示例文档中 TCP 示例的二维码写的是 `ServerPort=1883`，与"默认端口 502"矛盾 —— 疑似从 MQTT 示例复制遗漏【未知/待确认#15】。本项目 App 作为客户端连仪器，端口在 App 配置里填（默认 502），与仪器实际配置保持一致即可，不受该示例错误影响。

## 3. 寄存器分析（保持寄存器，191AF/191AF+ 通用）【事实】

> ⚠️ **本节结果块地址有误（其余条目与手册一致）。** 结果块不在 0x1C~0x1E，而在 **0x1F~0x23**：
> 0x1C = 温度判断上限、0x1D = 电压判断上限、0x1E = 电阻判断上限、**0x1F = 测试上传标志**、
> 0x20 = 测试保存温度、0x21 = 保存电压、0x22 = 保存电阻、**0x23 = 合格判定**；全表共 **36 个（0x24）**，
> 并非本节所说的 31 个（0x1F）。**最新对照表与实现以 §19 为准**；本节保留用于追溯。**

寄存器总数 **31 个（0x1F）**，地址 0x00~0x1E【事实：通讯示例文档"寄存器总数为 001FH"】。全部按**大端序**传输（高字节在前）【事实：示例 00EA=234】。通用写功能码 0x06（写单寄存器）。

| 地址 | 名称 | 类型/示例 | 单位/缩放 | R/W | App 用途 |
|---|---|---|---|---|---|
| 0x00 | 实时温度 | 数值，例 00EA=234 | ℃，**系数 0.1** → 23.4℃ | R | 测量页大屏显示 |
| 0x01 | 温度单位 | 0=℃，1=℉ | — | R/W | 显示换算前提【未知#5】 |
| 0x02 | 结果保存 | 0=手动，1=自动 | — | R/W | 可配置项（默认不写）【未知#6】 |
| 0x03 | 自动关机时间 | 0/5/10/15 分钟 | 分钟 | R/W | 可配置项（默认不写） |
| 0x04~0x09 | 备用 | — | — | — | 不读不写 |
| 0x0A~0x19 | 设备信息(扫码) | 字符串，按字节解析，16 寄存器=32 字节 | ASCII【推断，编码未知#2】 | R | 记录"设备SN"字段 |
| 0x1A | 设定温度(扫码) | 例 350 | ℃，**系数 1**（整数） | R | 记录"设定温度" |
| 0x1B | 误差范围(扫码) | 例 10=±10℃ | ℃，系数 1 | R | 记录"误差范围" |
| 0x1C | 测试上传标志 | 0=无效，1=保存按钮按下；**读取后自动清零** | — | R | 新结果检测（核心） |
| 0x1D | 测试保存温度 | 例 351 | ℃，**系数 1**（整数） | R | 记录"测量温度" |
| 0x1E | 测试合格判定 | 0=NG，1=OK | — | R | 记录"结果" |

**必须重点区分两条缩放规则【事实】**：
- `0x00` 实时温度：**系数 0.1**（寄存器值 ×0.1）
- `0x1A / 0x1B / 0x1D`：**系数 1**，寄存器值即整数 ℃（示例 350/10/351 均不带小数）

**解读**：0x1A/0x1B 是"测试对象工艺参数"（扫码 TSET/TERR 的镜像），0x0A~0x19 是扫码 SN 的镜像（"设备信息（扫码）"）【推断：三者的"（扫码）"标注 + 扫码指令 SN/TSET/TERR 名称一一对应】。0x1C~0x1E 是每笔测试结果通道。

> ⚠️ **2026-09-21 修订**：本段（含上面的地址表）是**旧固件版**文档的内容，已被 §19 的真机手册表推翻，**勿再引用**。
> 扫码指令也一并换版（`TERR` → `TMIN`/`TMAX`/`VMAX`/`RMAX`），见 §23。

【未知/待确认】详见 §12：#2 SN 字符串编码与最大长度；#5 单位切换是否影响 0x00/0x1D 数值（若 0x01=1 时 0x00 变 ℉，App 需按 0x01 解释）；#6 0x02"自动保存"的确切行为（自动模式下是否无需按保存钮即产生 0x1C=1？—— 若是，现场可设为自动，App 将完全无人值守，但需仪器实测确认）；#7 0x03 与 0x1C 的交互；#9 0x1D 是否可能带小数（TSET 若支持 0.5℃ 级工艺参数）。

## 4. MODBUS TCP 报文设计（字节级）

### 4.1 MBAP 头结构【事实 + 通用标准】

上位机→仪器（每帧）：

```
| 事务ID(2B) | 协议ID(2B) | 长度(2B) | 单元ID(1B) | PDU... |
  0001         0000        0006       01
```

| 字段 | 长度 | 取值 | 说明 |
|---|---|---|---|
| Transaction ID | 2B | 自增（例 0x0001） | 请求响应回显配对；**必须用 16 位自增计数，同一时刻在途请求必须配对等待**（响应中回显） |
| Protocol ID | 2B | 恒 0x0000 | MODBUS TCP 固定 |
| Length | 2B | 0x0006 | = 单元ID(1) + PDU 长度(5)；不含 MBAP 本身 |
| Unit ID | 1B | 0x01（可配） | 对应 RTU 从机地址概念，仪器忽略/校验未知【未知#10】 |

### 4.2 App 的实际轮询请求 —— 【推断】+【事实】

**方案：每个巡检周期发 1 个请求，一次读全部 31 个寄存器（0x00 起 0x1F 个）**：

```
TX: 00 01 00 00 00 06 01 03 00 00 00 1F
    ─── ─── ─── ─── ─── ── ── ───── ─────
     │   │    │    │   │   │  │    │    └─ Quantity=0x001F (31)
     │   │    │    │   │   │  │    └─ Start Address=0x0000
     │   │    │    │   │   │  └─ FC=0x03 读保持寄存器
     │   │    │    │   │   └─ Unit ID=0x01
     │   │    │    │   └─ Length=0x0006
     │   │    │    └─ Protocol ID=0x0000
     │   │    └─ Transaction ID=0x0001(低字节)
     └─ Transaction ID=0x0000(高字节)
```

```
RX: 00 01 00 00 00 43 01 03 3E <62字节寄存器数据...>
    长度=0x0043=67 = 1(UnitID)+1(FC)+1(字节数)+62(31×2)
```

一次全读的**依据**：
1. 示例文档明示"可以一次性读取全部数据，寄存器总数为 001FH"【事实】；
2. 结果快照一致性：0x1C（标志）+0x1D（温度）+0x1E（判定）+0x00（实时温度）+0x1A/0x1B（工艺参数）出自**同一响应**，时间戳完全对齐，消除多次请求间的仪器状态漂移；
3. 0x1C"读取后自动清零"若以仪器**完成一次读命令处理**为动作点【推断，见 §5.2】，则标志、温度、判定同帧取得后清零，丢失窗口最小化；
4. 流量：每轮 1 请求/响应 ≈ 150B，1s 周期完全无压力，不会导致仪器通讯超时。

> 备选方案：读 0x1C~0x1E（3 寄存器）短帧，理由同上但窗口无区别、且拿不到同快照的 0x00/0x1A/0x1B。**不采用**，全读更优。
> 设备信息 0x0A~0x19 随全读自然带回（32 字节），App 记录设备标识无需额外请求（实测为设备显示的字符串，作「设备信息」入库）。

### 4.3 异常与边界

- 仪器异常应答：`FC | 0x80` + 异常码（例 `83 01`=非法功能）。TCP 下无 CRC 校验【事实】，靠 Length 字段与帧结构校验。
- 响应 Length 与实际字节数不符 / 事务 ID 不匹配 → 丢弃、判超时重试【推断，属标准实现】。
- 仪器支持的最大 Quantity 无文档说明；31 < 125 标准上限，无风险【事实：全表仅 31 寄存器】。

## 5. 自动获取结果流程与可靠性分析

> ⚠️ **实机实测修正（2026-09-14，详见 §18）**：触发寄存器是 **0x1E**（按下=0x0014，**自行保持后清零**，
> 不存在文档所述「读取后自动清零」），判定是 **0x04**，目标/上下限是 **0x1B/0x1C/0x1D**。
> 本节推理中出现的 0x1C=1 / 0x1D / 0x1E 判定 等均为旧文档语义，**结论按新映射重读**：
> 「同帧全读」的论证与防护设计仍然成立，只是原子帧的成员变成了 0x1E + 0x04 + 0x02 + 0x00。

### 5.1 目标流程【事实 + 需求】

```
操作员测量 → 按仪器保存按钮 → 仪器：0x1E=0x0014（保持一段时间后自清）, 0x04=判定, 0x02=漏地电压
   ↑                                                        ↓
App 0.5s 轮询一次，读到 0x1E 由 0 变非 0 → 本帧内即含 0x04/0x02/0x00 → 写入本地库 → UI 弹结果
```

### 5.2 实测语义下的丢失窗口（2026-09 更新）—— ⛔ 结论已由 §19 修正

> **修正**：触发寄存器是 **0x1F（测试上传标志）**，结果值在 **0x20~0x23**。
> 实测（§19.4）：标志**置 1 后约 1 s 自动清零** —— 所以本节"限时保持"的推理方向**重新成立**，
> 窗口 ≈ 1 s；但"漏读即丢"已被 **补收通道** 缓解（签名变化即补记，见 §19.4）。
> 下方按旧前提书写，阅读时请把 `0x1E` 换成 `0x1F`、`0x1D/0x1E` 换成 `0x20~0x23`。

0x1E 的保持期（时长未实测）是**唯一的窗口**，且它是「自清」而非「读后清」，因此：

| 场景 | 结论 |
|---|---|
| 保持期内 App 读到该帧 | 不丢（且保持期内重复读到不会重复入库 —— App 用「值变化」判定新保存） |
| 保持期结束前 App 未连上（Wi-Fi 断/仪器关机/App 未启动） | **该笔丢失** —— 仪器只保留最新一笔，标志自清后无从补收 |
| 已读到帧、DB 写入前 App 崩溃 | 不丢：pending 通道先落盘再幂等入库，重启补记（见 §7） |
| **保持期内操作员又按一次保存** | 0x1E 不回 0，值变化检测会漏 —— 已补**内容签名**兜底（判定+目标+上下限变化即记第二笔）；两次结果内容完全相同的连按无法区分，属仪器侧信息缺失 |

> 与旧方案的差别：旧文档的「读后清零」需要 App 主动读才清，理论上离线期数据一直挂着；
> 实测的「限时保持」意味着**离线期间的结果一定会丢**，只能靠「保持时长足够长 + 0.5s 轮询」压缩概率。
> 若现场要求零丢失，需请厂家确认保持时长，或询问是否有历史/批记录寄存器（0x1F 之后或扩展功能码）。

### 5.3 为什么必须一次全读 0x00~0x23（同帧全读）【原推理，映射按 §19 修正】

> 地址对应：下文旧文档的 `0x1C`（标志）→ 现 **0x1F**；`0x1D/0x1E`（保存温度/判定）→ 现 **0x20 / 0x23**。
> 手册已明确 0x1F「读取后自动清零」，故下文"清零发生在请求到达时 / 响应发送时"的两种可能**仍然要实测确认**：
> 若先清后快照，本笔会漏检（数据仍在仪器上，但 App 无感知）。

假设分两次请求：先读 0x1C 返回 1，随后仪器清零；第二次读 0x1D 前 App 崩溃或网络中断 → **0x1D/0x1E 未取到且 0x1C 已清，该笔数据永久丢失**。这是协议层面最大的丢失窗口。

同帧全读后，仪器对**一个**读请求产生响应快照，0x1C=1 与 0x1D/0x1E 从同一快照解析：
- 若仪器清零发生在"响应发送时"→ 快照内三个值完整有效，App 拿到即安全；
- 若仪器清零发生在"请求到达时"（先清再快照）→ 0x1C 将读回 0，本笔**漏检但未丢**（App 下轮无感知，数据仍悬在仪器上直到下一次保存覆盖）—— 此行为**必须实测确认**（测试 C：按保存后立即读；测试 D：连续两次读看是否 0x1C 先 1 后 0 但 0x1D/0x1E 同帧有效）。

**App 侧防护**：确认点 =「收到含 0x1E 非 0 的响应」即事务开始，DB 写入成功即事务结束，中间不退出（见 §6 状态机）；崩溃重启后通过 pending 恢复（pending 内容 = 触发帧解析出的记录，重试插库被幂等键吸收）。

### 5.4 可靠性边界（必须对用户/厂家讲清楚）【旧文档语义，结论见 §5.2】

| 场景 | 行为 | 结论 |
|---|---|---|
| App 连接中，操作员连续快速保存两笔 | 0x1C 是单寄存器"最新一笔"【推断】；1s 周期内若两笔都落定 → 第二笔覆盖第一笔标记，第一笔仅当 0x1D 仍指向最新一笔才可读 | 高风险【未知#7 需确认两笔最小间隔与覆盖行为】 |
| App 离线（Wi-Fi 断/仪器关机），期间按保存 | 若仪器保留标志等待上位机读取 → App 恢复后补收（不丢）；若仪器重启清 0x1C → 丢 | 无法保证【未知#4 需实测测试 G】 |
| 读 0x1C=1 帧已收到、DB 写前 App 崩溃 | 下轮重读，0x1C 已清 → 该帧数据已随崩溃丢失（毫秒级窗口） | 防护：读帧→立即插库在同一协程内完成；崩溃只发生在极端情形【推断：窗口极小但存在，测试 E 观察】 |

> **结论：协议本身没有"每笔独立编号/历史缓冲"能力【推断：0x1C~0x1E 只描述最新一笔，未发现历史缓冲寄存器】，所以「操作员按保存」与「App 入库」之间只要存在间隙就有理论丢失可能。App 能把窗口压缩到~毫秒，但**若现场要求 100% 不丢，必须请厂家确认**：(a) 0x1C 是否在无连接时保持=1 并保留 0x1D/0x1E；(b) 连续保存两笔的最小间隔；(c) 是否存在未公开的历史/批寄存器（例 0x1F 之后或功能码扩展）。**

## 6. 状态机设计

> ⚠️ 下图中 `0x1C=1` 为旧文档语义；**实测触发条件为「0x1E 非 0 且与上一帧不同」**（见 §18）。
> 状态流转与「读到即入库、入库前置 pending」的防护设计不变。

单连接单事务，全程**一个专用轮询协程**顺序执行（无并发读写仪器），状态对外以 StateFlow 暴露。

```
         ┌───────────────────────────────┐ 掉线/异常
         ▼                               │
    DISCONNECTED ──connect()──▶ CONNECTING ──socket ok──▶ CONNECTED
         ▲                                  │                  │
         │            connect 失败/超时      ▼                  ▼
         └──────────── RE-CONNECTING ◀── NETWORK_ERROR ◀── POLLING
                              │  (指数退避: 1s,2s,4s...30s 封顶)   │
                              └─────── 成功 ─────────────────────┘
   POLLING（每 pollInterval 一次，默认 1000ms）
      │  readAll(0x00, 0x1F)
      ├─ 响应 OK 且 0x1C=0 → 更新实时温度/工艺参数 → 回 POLLING（下一拍）
      ├─ 响应 OK 且 0x1C=1 ─▶ RESULT_READY（快照已含 0x1D/0x1E，挂起后续轮询）
      │        │
      │        ├─ DB 事务写入成功 ─▶ 幂等键登记 ─▶ UI 广播结果 ─▶ 回 POLLING
      │        └─ DB 写入失败 ─▶ 本地重试(3次) ──仍失败──▶ 标记 ERROR + 界面告警
      │                                                  （数据保留在内存快照，不静默丢弃）
      └─ 超时/IO 异常/异常响应 ─▶ NETWORK_ERROR（连读失败计次；连续 N 次判定断线→DISCONNECTED）
```

| 状态 | 进入条件 | 行为 |
|---|---|---|
| DISCONNECTED | 启动/用户停止/断线确认 | 空闲，不占 socket |
| CONNECTING | 用户启动或自动重连 | TCP 连接 + 首帧试探读；超时 = socketTimeout(默认 2s) |
| CONNECTED | socket 建立 | 立即转入 POLLING |
| POLLING | 每周期 | 执行全读；本帧无新结果则**不回写任何寄存器** |
| RESULT_READY | 0x1C=1 | 暂停轮询直至入库完成（防并发重入） |
| NETWORK_ERROR | 读超时/IO | 关闭 socket → RE-CONNECTING（退避） |
| ERROR（数据面） | 入库失败重试耗尽 | UI 红色告警条，保留快照等待手动重试 |

**防重复保存**：每次 RESULT_READY 生成 `snapshotId = hash(时间戳+0x1D值+0x1E值)`，写入前查本地库是否已存在同 ID（唯一索引冲突忽略）；DB 事务内完成"插入 + 标记"，天然幂等。由于快照来自仪器清零前唯一一帧，同一帧不可能被解析两次（0x1C 已清），幂等键是双保险而非主机制。

**生命周期**：轮询协程挂在前台服务（见 §10.3）；Activity 销毁不停止采集；App 冷启动先读本地配置再自动连。

## 7. 数据丢失风险专项分析（Prompt §32 的逐条回答）

| 问题 | 回答 |
|---|---|
| App 读 0x1C 后清零、读 0x1D 前崩溃，会丢吗？ | **存在该风险（分帧读取设计下）**。本设计用**同帧全读**规避：0x1D/0x1E 与 0x1C 在同一响应内到达，不存在"已清零但未取数据"的中间态【推断：依赖仪器"响应快照式清零"，需实测】 |
| 是否一次请求读 0x1C~0x1E？ | 是 —— 并进一步一次全读（§4.2），同快照还含 0x00/0x1A/0x1B |
| 是否先读 0x1D/0x1E 再读 0x1C？ | 无意义：0x1D/0x1E"0x1C=1 时有效"，先读可能读到上一笔残留；快照式读法才自洽 |
| 如何减少失败窗口？ | 单协程串行 + 收到帧立即入库 + 入库失败重试保留内存快照 + 前台服务保活（防进程被杀） |
| 是否需要本地 pending 状态？ | 需要（Room 表 pending_results，崩溃恢复后若 0x1C 已清但 DB 无记录，用 pending 补记 —— 实测确认 0x1C 行为后再定级） |
| 必须厂家确认的问题 | #4（离线保存滞留）、#7（连续保存间隔/覆盖）、#8（是否有一笔=寄存器只读后清零的全流程）、#13（是否存在更多结果寄存器） |

## 9. 数据库设计（Room + SQLite）

**评估**：本项目 4 张表、DAO 间关联与组合筛选多，Room 提供编译期 SQL 校验、Flow 响应式查询、事务注解，且 **Room 就是 SQLite 的封装**（同一存储文件，无多余依赖成本）→ **采用 Room 2.6.1 + KSP**。若未来构建链出问题，回退方案为旧项目验证过的裸 SQLiteOpenHelper（表结构不变，DAO 换手写 SQL）。

```sql
Line(id PK, name UNIQUE NOT NULL, enabled, createdAt, updatedAt)
Model(id PK, name UNIQUE NOT NULL, enabled, createdAt, updatedAt)
DeviceConfig(id=1 单行, name, ip, port, unitId, pollIntervalMs, timeoutMs, enabled)
MeasurementRecord(
  id PK AUTOINCREMENT,
  snapshotId UNIQUE,          -- 幂等键 (§6)
  timestampMs,
  lineName, modelName,        -- 冗余快照：线别/机种改名或删除不影响历史溯源
  deviceId(SN 字符串, 仪器0x0A~0x19), deviceIp,
  setTemperature,             -- 0x1A (整数 ℃)
  measuredTemperature,        -- 0x1D (整数 ℃)；0x00 仅实时显示不落历史
  tolerance,                  -- 0x1B (±℃)
  result,                     -- OK / NG（由 0x1E 判定，App 不自行判定【事实】）
  rawHex?（调试期可选，正式版移除）
)
ConfigMeta(key PK, value)     -- 上次选中线别/机种、导出路径等界面态
```

**取舍说明**：历史记录不存外键，只存线别/机种**名称快照** —— 工厂场景线别机种被删改后历史报表必须仍可溯源；筛选用名称 + 时间索引。查询筛选（日期区间/线别/机种/OK NG/关键词）走 DAO 组合查询，Flow 驱动历史页实时刷新。

## 10. 配置文件方案

**分析结论：Room 即配置真源（单写单读），JSON 文件仅作"配置包"导入/导出载体**，不做双写同步 —— 双写会产生一致性难题，违背"配置文件不能影响数据库存储"的要求。

- 导出：线别表 + 机种表 + 设备配置（含上次选中态）→ 序列化 JSON → `配置备份_yyyyMMdd.json`（系统分享/拷贝）。
- 导入：读 JSON → 事务内 upsert（名称冲突策略：默认"跳过并列出冲突"，提供"覆盖"选项）→ **绝不触碰 MeasurementRecord**。
- 密码类字段（仪器 WiFi 密码）不在此方案范围（那是 191AF+ 侧扫码配置的内容）；App 侧不需要存 WiFi 密码。

**复刻到另一台平板**：新平板装 App → 配置页导入 JSON → 完成（含仪器 IP 等）【推断：可满足 Prompt §14 需求】。

## 13. 通信模块：自实现 vs 第三方库

| 方案 | 评估 |
|---|---|
| jlibmodbus / modbus4j | PC 向库，Android 兼容与维护一般；现代 modbus 库活跃度普遍低 |
| **自实现（java.net.Socket + 帧编解码）** | **采用。** 本项目协议面极窄（仅 FC03 读全表 + 可选 FC06 写单寄存器，TCP 无 CRC），自实现 <200 行，可完整控制超时/重连/日志；旧项目 net/Modbus.kt 已验证自研编解码路径；无第三方依赖 = 无供应链与版本风险，符合工业长期维护原则 |

关键实现点：同步阻塞 IO + 独立协程（Dispatchers.IO）；SO_TIMEOUT = timeoutMs；事务 ID 16 位自增；每响应校验 MBAP 长度与回显；协议级超时计次驱动断线判定。

## 14. 网络异常处理设计（Prompt §20/§31 覆盖）

| 场景 | 处理 |
|---|---|
| 仪器断连/关机 | 连续 2 次读失败 → 判定断线 → 关闭 socket → 指数退避重连(1,2,4…30s 封顶)，UI 显示"重连中 (第n次)" |
| Wi-Fi 断开（平板侧） | ConnectivityManager 网络回调触发；无网时暂停重连协程，恢复后立即重连 —— 补上 Android 13+ 网络状态查询限制的兼容写法 |
| App 退后台 | 采集在前台服务（CollectionService，前台通知"测量收集中"），轮询不中断；**数据不因界面销毁而丢** |
| 屏幕休眠（平板无人值守） | 前台服务持 PARTIAL_WAKE_LOCK + 测量页 FLAG_KEEP_SCREEN_ON（可配置）—— 保证 TCP 长连接不被 CPU 休眠掐断；Wi-Fi 睡眠策略设"始终连接"【推断：系统级，App 内申请 Wi-Fi lock 兼容】 |
| 解析错误 / 异常响应 | 计次跳过本帧，不崩溃；连续异常按断线处理 |
| 恢复后补收 | 若 0x1C 仍=1 → 正常流程补收（前提仪器保留标志，见 §5.3 边界） |

## 15. 通信验证方案（Phase 2 工具功能 ← 映射 Prompt §8 测试 A~G）

> ⚠️ 本节测试项按**旧文档语义**编写，其目标（A~G）已由 §18 的实机实测一次性回答；
> 保留作为「若换机型/换固件时的回归验证清单」，验证 App 内已由**诊断页帧日志 + 手动全读 PROBE** 承担。

Phase 2 交付最小验证 App（独立模块/独立 APK，不进正式包），界面：连接参数输入 + 6 寄存器实时读数面板 + 原始帧 hex 日志 + 自动 1s 轮询开关。日志行如：
```
[22:31:01] CONNECT 192.168.1.100:502 OK
[22:31:02] TX 0001 0000 0006 01 03 0000 001F
[22:31:02] RX 0001 0000 0043 01 03 3E ...  0x00=3526(0.1→352.6℃) 0x1A=350 0x1B=10 0x1C=0
[22:31:03] RX ... 0x1C=1 0x1D=351 0x1E=1  → 一次快照已含全部字段
```
| 测试 | 目的 | 通过标准 |
|---|---|---|
| A 连接后静置读 | 基线值域 | 记录 0x1C~0x1E 初始值 |
| B 不测量持续读 | 0x1C 空闲稳定 | 长时间保持 0 |
| C 保存后立即读 | 触发时序 | 0x1C=1 且同帧 0x1D/0x1E 有效 |
| D 连读两次 | **清零时机（设计生死线）** | 第 1 帧 1/温度/判定齐，第 2 帧 0x1C=0 → 证实快照语义 |
| E 连续两次保存 | 是否丢/覆盖 | 两笔都能在"自动清零前"被读到 |
| F 轮询中随机按保存 | 自动发现 | 无需任何操作 1~2 帧内发现 |
| G 离线期保存→恢复 | 滞留还是丢失 | 若 0x1C 滞留=1 → 补收成功（可靠）；若清空 → 向厂家反馈并重新评估 §7 风险等级 |
| 附测 | 全读(31)与分读(3)行为差异 | 观察清零语义是否一致 → 确定正式版请求方式 |

**测试 D/G 的结论直接决定正式版的两处设计**：请求粒度（§4.2）与 pending 机制（§7）。工具同时输出供厂家追查的复现日志。

### 19.2 旧实测为何错：错位一格 + 读长度截断【事实-手册 + 推断】

**读长度截断（可直接验证）**：App 当时只读 `0x00~0x1E` 共 31 个寄存器 —— 恰好停在结果块（0x1F~0x23）**之前**。
所以"触发标志、保存温度、判定"三件套一个都读不到，只能拿别的寄存器凑语义。

**错位一格（推断）**：用户早期清单的 26/27/28/29/30 号 = 手册 0x1B/0x1C/0x1D/0x1E/0x1F，即**编号整体 +1**。
将错位后的观测逐条对回手册，全部得到解释：

| §18 观测 | 手册解释 |
|---|---|
| 0x04 = "判定结果，0=NG 非 0=OK"，3 次实测值 1、1、2 | 0x04 = **测量通道**，值 1/2 = 漏电压/电阻通道 —— 与判定无关 |
| 0x1E = "结果保存标志"，按下 = 0x0014(20)、保持一段时间后自清 | 0x1E = **电阻判断上限**，手册默认 **20 = 0x0014**；"自清"是误判（该寄存器恒为默认 20，「按下才变」属操作相关性巧合） |
| 0x1A = 未知、0x1B = 设定温度、0x1C = 下限、0x1D = 上限 | 手册：0x1A 设定、0x1B 下限、0x1C 上限、**0x1D 电压上限** —— 正是错位一格 |
| 0x03 = 自动关机时间 | 0x03 = **实时电阻**（顺推 0x02 = 实时电压，§18 自己记的是"漏地电压 ×0.1"，值域吻合） |
| "保存温度找不到，实时温度不定格" | 真值在 **0x20**，此前根本没读到 |
| "0x1E 保持多久未知" | 触发是 **0x1F 读后即清**，不存在保持期 |

**教训（写入开发纪律）**：寄存器清单只能从**原始手册页**推导，不能靠"编号顺序 + 数值巧合"反推；
读长度必须覆盖手册全表，遇到异常码再降级 —— 截断在结果块之前会让所有结果字段静默失效，
而现象（有读数、有变化）看起来却完全正常。

### 19.4 真机补充实测（2026-09-14）：0x1F 保持约 1 s 后自清【事实-实测】

用户实测：`0x1F` 置 1 后**约 1 秒**自动清零 → 轮询周期必须 **< 1 s**。

**App 侧应对（v4.1）**：

| 项 | 处理 |
|---|---|
| 轮询周期 | 默认 **900 ms**（原 500 ms 亦可，用户定为 0.9 s；配置页可改）—— 只剩 0.1 s 余量 |
| 同笔读两帧 | 1 s 窗口 > 0.9 s 周期 → 同一笔可能被两帧读到：靠**结果签名**相同跳过（去重由"兜底"变成"必需"） |
| 读晚了（补收） | 若某周期因 Wi-Fi 抖动 + 入库耗时略超 1 s，标志已自清 → 结果块签名已变即**补收**该笔，日志标注「（补收）」；判据三重：结果块存在 + 判定合法(0/1/2) + 签名变化。开关 `MeasurementController.RECOVER_MISSED_SAVE`，若真机发现结果块会被非保存操作改写则置 false 退回纯标志触发 |
| 签名必须收窄 | **修正**：签名原含 `0x04` 通道与 `0x1A` 设定温度 —— 这两者在**不保存**时也会变（操作员切通道/改设定），若保留会让补收通道把这类操作误记成结果。现签名 **只含 0x20~0x23**（单测已锁：切通道/改设定温度/实时量变化均不改变签名） |

> **残余丢失窗口（诚实标注）**：① App 刚连上时若正处于标志窗口内，该帧被当作基线丢弃；
> ② 两笔保存的 `0x20~0x23` **完全相同**时只能靠标志脉冲区分，脉冲漏读即无法补收（仪器侧信息缺失）。

### 19.5 尚未真机验证的点（诚实标注）【未知】

- `0x1F` 自清是"计时自清"还是"读后计时清"（本次实测为计时约 1 s；两种模型对 App 行为等价：
  周期 < 1 s 都能读到，读晚了都靠补收）—— 真机可按保存后立即连读两次确认
- `0x20` 是否等于仪器屏幕上定格的测量温度（手册称"测试保存温度"，值域 ×1 ℃）—— 需与屏幕比对
- `0x0A~0x19` 究竟写的是设备 SN 还是 Wi-Fi 字符串（§18 记 Wi-Fi，手册记设备信息）：App 只当**设备标识**用，
  两种解释下用法相同，不影响功能
- 老固件是否真的没有 `0x1F~0x23`（降级路径目前只有单测覆盖，无真机样本）
- 结果块是否只在保存时被写（补收通道成立的前提）—— 真机连续观察 N 帧：不操作时 `0x20~0x23` 应恒定不变

## 21. 真机体验后的 7 项修改（2026-09-20，v6）

> 用户在真机安装使用后提出 7 点。本节**同时包含寄存器层之外的应用层改动与通信链路的加固**。
> 寄存器语义（§19 的表、0x1F 触发、0x20~0x23 结果块）**一行未改** —— 见 21.4 的说明：
> 厂家 V1.1 协议文档的地址表与真机固件不是同一版，寄存器层一律以真机实测为准。

### 21.1 多保存一笔 → 弹卡期间暂停读取；只保留 OK【需求 + 缺陷】

用户反馈："保存数据时会多保存一笔"。

**根因（代码侧，已定位）**：轮询周期写成了「读 → `delay(900)`」，实际周期 = **读取耗时 + 900ms**，
Wi-Fi 一抖动就 >1000ms，而 `0x1F` 窗口只有约 1s → **经常性读晚**，于是频繁走「补收」通道；
补收判据是「结果块内容变了就算一笔」，只要固件在非保存时刻也刷新 `0x20~0x23`，就会多记一笔。

**改法**（两道）：
1. **固定周期调度**：`nextDelay(cycleStart, interval)` —— 本轮耗掉多少补多少，周期恒等于配置值，不再累积读取耗时；
2. **弹卡期间暂停轮询**（用户明确要求"全屏显示完后再继续读取数据"）：`MeasurementController.hold(5s)`，
   弹卡消失后恢复；**恢复后的第一帧只重建基线，不判定也不补收** —— 暂停那几秒里仪器上的任何变化都不会被当成本笔结果。

暂停有两道保险：`HOLD_MAX_MS = 15s`（界面异常时不至于永久停摆）；且远小于仪器协议文档第 3 页
「超过 60 秒无交互则判通讯超时」的阈值。

> ⚠️ **2026-09-21 修订**：用户随后反馈「更新后断连更频繁」，而这一版**新增的唯一静默时段**就是这条
> 「弹卡期间完全不发请求」。已改成 **「照常读、但不判定不记录」**（数据行为完全一致，链路保持热）。
> 完整推理见 §22.4。

**只保留 OK**（用户要求："现在不需要保存 NG 的信息，只保留 OK 的即可"）：

| 情形 | 处理 |
|---|---|
| `0x23 = 1`（OK） | 入库 + 全屏弹卡 + 振动 + 自动学习设备编号 |
| `0x23 = 0`（NG）/ `2`（无效） | **不入库、不弹卡、不振动**，诊断日志留一行 `○ NG 不入库：…`（不静默） |
| 降级模式（无结果块，读不到判定） | **一律不入库**（无法确认是否合格 → 宁可不下结论，也不编造一条 OK），日志告警一次 |

> ⚠️ 与"不静默丢数据"的关系：NG 不入库是**用户明确要求的业务规则**（不是数据丢失），
> 且诊断日志有痕、界面上"最近结果"卡片写明「只记录判定为 OK 的测量」。
> 同时**移除**了降级模式下的推测判定（原实现按 `0x04` 非 0 猜 OK）—— 那是编造数据，已删除。

**判定逻辑抽成纯函数类 `collect/SaveTrigger.kt` 并加 12 例单测**：现场最怕多记/漏记，
把这唯一决定记录条数的地方从轮询循环里提出来，用测试守住（含"同一笔被两帧读到只记一次"、
"连续两笔内容完全相同靠标志脉冲分辨"等真机场景）。

### 21.2 记录详情不再显示寄存器原始地址/值【需求】

明细弹窗去掉 `0x04 / 0x1A / 0x1B~0x1C / 0x1D / 0x1E / 0x20 / 0x21 / 0x22` 前缀，
以及"判定来源 0x23""触发来源 0x1F"两行说明 —— 只显示换算好的值（用户："反正没人会去深究寄存器的原始数据"）。
标签同时对操作员口径统一：`保存电压/保存电阻` → **测量电压/测量电阻**，`温度判断` → **合格区间**。
需要核对寄存器时走「诊断」页的帧日志，那里的 hex 才是该被深究的地方。**导出 XLSX 的列名不变**（数据交换格式）。

### 21.3 偶发通信断连：代码侧排查与加固【缺陷】

用户："偶然会出现通信断连的情况，无法判断是代码问题还是设备硬件问题"。代码侧共找到 5 处问题（全部已改）：

| # | 问题 | 改动 |
|---|---|---|
| 1 | **任何异常都断线重连**：一次 MODBUS 协议级异常应答（如异常码 03）就让整条连接重来，现场表现为"断连" | 协议级异常 = 仪器听懂了但拒绝这一条，**TCP 链路是好的** → 保持连接、记日志、继续读；连续 5 次才认定链路也坏了 |
| 2 | **`Socket.isConnected` 判断在线不可靠**：TCP 对端断开后它仍为 `true`，只能排除本地已关闭 | 补上 `isInputShutdown/isOutputShutdown`，并**在注释里写明它不能用于判断仪器在线**（真正发现靠读操作抛异常） |
| 3 | **半开连接发现太慢**：AP/仪器静默掉线时只能等下次请求超时 | 连接开启 `keepAlive`，由内核探活 |
| 4 | **响应帧过短会抛 `ArrayIndexOutOfBoundsException`**，错误信息看不出是通信问题 | `readHoldingRegisters` 先判长度再取下标，统一成 `IOException` |
| 5 | **无法判断"断连"的性质**：日志只有一句"连接失败" | 断线日志带上**连接时长 + 成功读取帧数 + 原因分类**（读超时/异常应答/对端断开/网络中断），例：`⚠ 对端断开连接…（已连接 12 分 34 秒，成功读取 812 帧）` |

**未改动、也无法靠代码解决的部分**（诚实标注）：Wi-Fi 信道/AP 漫游抖动、仪器侧重启或掉线、
平板省电策略 —— 这些要靠上述日志区分：**连了几小时才断 = 环境/设备侧；连上 5 秒就断 = 值得继续查代码**。

### 21.4 温度设置 + 设备编号 + 组合配置二维码【需求】

**先澄清一个文档冲突（重要）**：用户提供的《191AF 测温仪 MODBUS 通讯协议 V1.1》**地址分配表与真机固件不是同一版** ——
该文档是旧版（`0x1C`=上传标志、`0x1D`=保存温度、`0x1E`=判定，且**没有**电压/电阻/通道寄存器），
而本机真机是 `0x1F` 标志 + `0x20~0x23` 结果块（实测标志置 1 后约 1 s 自清、记录能正常入库；
若真机是旧版，App 会降级到 `0x00~0x1E` 并且**一笔都不会入库**）。**寄存器层继续以真机实测为准，未按该文档改。**

但该文档的**扫码配置指令**与固件版本无关，可直接照用（用户给的示例：`SN=QK-HT-001,TSET=350,TERR=20`）：

| 指令 | 含义 | 对应寄存器 |
|---|---|---|
| `SN` | 设备信息/编号 | `0x0A~0x19`（32 字节 ASCII） |
| `TSET` | 设定温度 ℃ | `0x1A` |
| `TERR` | 误差范围 ±℃ | `0x1B`（旧版文档语义；新版固件里对应判断上下限 `0x1B/0x1C`，由**仪器自己**换算，App 不管） |

多指令用**英文逗号**分隔，字符须为英文状态（`±` 是显示符号，绝不进二维码 —— 有单测挡住）。

> ⚠️ **2026-09-21 修订**：上表已作废 —— 该文档的**通用指令表同样是旧固件版**（`TERR` 对应旧固件的 `0x1B` 单个 ± 值）。
> 现按厂家新版《扫码配置指令》发 `TSET` / `TMIN` / `TMAX` / `VMAX` / `RMAX`，判断依据与换算见 **§23**。
> 下面这几段保留原样，只为留下当时的推理过程（数据层/界面的结构没变，只是指令集换了版）。

**数据层（DB v5 → v6，纯新增两张表）**：
- `temp_preset`：`name`(自动生成 "350±20") / `setTemp`(TSET) / `tolerance`(TERR) —— 新增时**只输两个数字**，名称自动生成
- `device_sn`：`name` / `source`（`manual` 手输 / `learned` 仪器读到自动收录）

## 22. 「更新后断连更频繁」的排查与三处加固（2026-09-21）

【现象】用户：*"wifi连接的代码在什么位置，为什么这次更新后断连的现象反而更加频繁了"*。
这是**更新引入的回归**，必须当成缺陷查，不能拿"网络本来就不稳"搪塞过去。

### 22.1 先回答「代码在哪」

| 文件 | 职责 | 关键位置 |
|---|---|---|
| `net/ModbusTcpClient.kt` | **唯一碰 socket 的文件**：建连、发帧、收帧、超时 | `connect()` / `exchange()`（写 + 等回应，超时在此抛）/ `disconnect()` / `isConnected` |
| `collect/MeasurementController.kt` | **连接管理**：何时连、何时断、断了怎么重连、轮询节奏 | `runLoop()`（外层重连 + 内层轮询）、`nextDelay()`、`errKind()` |
| `collect/CollectionService.kt` | 前台服务保活（不改变网络行为） | — |
| `data/db/Entities.kt` | 参数：轮询 **900ms** / 连接与读超时 **2000ms** | `DeviceConfig` |

### 22.2 那一版在"网络路径"上到底改了什么

| # | 改动 | 对断线的方向 |
|---|---|---|
| 1 | 轮询改**固定周期**（原来实际周期 = 读耗时 + 900ms ≈ 950~1000ms） | 请求略密 ⚠ |
| 2 | **弹卡 5 s 完全不发请求**（新增的静默期） | 新压力 ⚠（§22.4） |
| 3 | 协议级异常不再立刻断线，容忍 5 次 | 只会减少断线 ✅ |
| 4 | `keepAlive = true` | 中性（更早发现真断） |
| 5 | `isConnected` 加半关闭判断 | **死代码，无行为差异**（见 22.6） |
| 6 | 每笔 OK 多两次 DB 写（学习编号 + 清空选择） | 那一轮变慢 ⚠ |

### 22.3 确定性缺陷（已修）：固定周期**没有下限** ⭐

```kotlin
// 09-20 那版：
(intervalMs - (now - cycleStartMs)).coerceAtLeast(0L)      // ← 可以算出 0
```

某轮耗时一旦 ≥ 周期（Wi-Fi 抖一下、仪器慢一点、刚保存完那轮要做 5 次 DB 往返），
剩余时间算成 **0** ⇒ **立刻发下一个请求**，而且会持续这样 —— 变成了背靠背连发。

**旧写法反而更宽容**：`读 → delay(900)` 无论多慢，**永远白给链路一个完整周期的静默**。
所以这是那一版中**唯一会主动加大链路压力**的改动：链路已经开始吃力时，新代码不但不给喘息，
还继续按最快速度压——更容易超时、更容易被判成"断连"。

**修法**：`MIN_CYCLE_GAP_MS = 200ms` 下限；顺带把协议异常的重试从「抢跑 500ms」改回**按正常周期**
（异常应答说明仪器活着但拒绝了这一条，抢跑只会让它更忙）。

### 22.4 最大嫌疑（已按用户拍板改掉）：弹卡那 5 秒静默 ⭐

那是这一版**新增的、App 完全不发请求的时段**。协议文档只写了「上位机发送间隔不要超过 60 秒，
否则测温仪认为通讯超时」——**那是它判上位机超时的口径，不代表它自己 socket 的空闲回收时间**。
若仪器（或 AP）的空闲回收短于 5 秒，就会变成：

> 每保存一笔 OK → 停 5 秒 → 连接被收掉 → 恢复后第一帧直接 EOF → 重连

现场表现正是「断连变频繁」，而且**几乎每一笔保存都来一次**，时间上与用户反馈完全吻合。

**用户 2026-09-21 拍板**：弹卡期间**继续读，但不判定、不记录**。
关键是这两种做法**数据行为完全一致**：

| | 完全暂停 | 继续读但不记录（现行） |
|---|---|---|
| 卡显示期间仪器上有新保存 | 不读 → 不记 | 读到了但**不判定** → 不记 |
| 卡收起后第一帧 | `rebaseline`，不判定不补收 | 同左 |
| 卡没消失前会多记一笔吗 | 不会 | **不会** |
| 链路 | 5 秒静默 | 一直热着 |

> 顺带：`0x1F` 的"读取后自动清零"语义在这里帮了忙 —— 卡期间被我们读掉的标志，
> 不会在卡收起后被判成新结果（`rebaseline` 已把签名推进到最新）。

### 22.5 新增诊断设施：让"代码还是硬件"能被数据回答

帧日志只有 500 行（≈4 分钟），断线原因会被收发帧刷掉，一眼看不出频次。新增：

- **断线原因计数**（`MeasureUiState.dropStats`，跨整个运行期累计，诊断页展示一行）：
  `断线统计（自本次启动）：读超时（仪器未应答） 3 次　对端关闭连接 12 次`
  - 「**读超时**」为主 → 链路/仪器侧（Wi-Fi 抖动、仪器忙）
  - 「**对端关闭**」为主且每段连接都很短 → 被主动踢（别的客户端连过仪器？仪器/AP 空闲回收？）
  - 「**仪器异常应答**」为主 → 协议/寄存器层面，**那才可能是 App 的问题**
- **日志窗口 500 → 2000 行**（约 15 分钟），并把已有证据串起来：
  `⚠ 对端断开连接（仪器/AP 主动关闭）（已连接 3 秒，成功读取 3 帧）…`
  —— 「连了 3 秒」和「连了 42 分钟」是两种完全不同的问题。

### 22.6 明确排除的（不能靠猜，要能说清为什么）

| 怀疑点 | 结论 |
|---|---|
| `isConnected` 加了 `isInputShutdown/isOutputShutdown` | **死代码**：`closeLocked()` 已把 `sock` 置 null，那两个判断永远走不到；且对端关闭不会置位这两个标志。无行为差异 |
| 协议异常容忍 5 次 | 只可能**减少**断线 |
| 每笔 OK 多两次 DB 写会不会把 DB 异常升级成断线 | 不会：`storeResult` 整段有 try/catch、`learnDeviceSn` 用 `runCatching`。它只**拉长那一轮**，那个后果由 22.3 的 200ms 下限兜住 |
| 断线退避记忆（连接短命时不把 attempt 归零） | **评估后不采纳**：若断线是"频繁但可恢复"（如 22.4 那种），退避递增会让**失联时间从 1 秒变成 30 秒**，宁可快速重连 |

### 22.7 尚未验证 / 未知（诚实标注）

- **22.4 是否真是主因，还没有真机证据** —— 判据是新装的断线统计：若「对端关闭连接」占多数、
  且日志里每段连接只有 3~6 秒，就是它；若「读超时」占多数且每段连接都很长，则与环境/仪器侧有关，
  本次更新的责任很小。
- **仪器/AP 的 TCP 空闲回收时间未知**（协议文档只给了 60s 的"上位机超时"口径，不是同一件事）。
- `keepAlive = true` 保留：理论上只会更早发现真断，个别 ROM 的省电 Wi-Fi 下可能由内核判死链路，
  存疑时一行即可回退。
- 本轮改动（下限、弹卡语义、计数、日志窗口）**均未真机验证**，只过了 35 例单测与编译。

## 23. 漏电压上限 / 接地电阻上限 与扫码指令集换版（2026-09-21，v7）

需求原话：「还要增加漏电压上限和接地电阻上限的配置，参考温度配置，需提前设置，温度/漏电压/电阻，这三个无论那个有选择都可以生成配置二维码」，附厂家《扫码配置指令》表 1 截图。

### 23.1 先说一个**必须纠正的事实**：指令集换版（`TERR` → `TMIN`/`TMAX`）

| 来源 | 通用指令表 | 组合示例 |
|---|---|---|
| 文本《191AF 通讯协议 V1.1》（2024-02-04） | `SN` / `TSET` / **`TERR`** | `SN=QK-HT-001,TSET=350,TERR=20` |
| 用户提供的《扫码配置指令》表 1 截图 | `SN` / `TSET` / **`TMAX`** / **`TMIN`** / **`VMAX`** / **`RMAX`** | `SN=QK-HT-001,TSET=350,TMIN=340,TMAX=360` |

**两者不是同一版固件，且新版与真机寄存器一一对应：**

| 新指令 | 真机寄存器（手册《地址分配》表） |
|---|---|
| `TMIN` | `0x1B` 温度判断下限 |
| `TMAX` | `0x1C` 温度判断上限 |
| `VMAX` | `0x1D` 电压判断上限 |
| `RMAX` | `0x1E` 电阻判断上限 |

而 `TERR`（单个 ± 误差范围）恰好对应**旧固件**的 `0x1B` —— 就是 §19 里已经确认「地址表与真机不是同一版」的那一批老文档。
这与 §19 对**地址表**的判断是**同一个结论的两次独立证据**：该 PDF 的通用指令表也是旧版的。

**所以：`TERR` 从二维码里删除，改发 `TSET` / `TMIN` / `TMAX`。** 界面输入方式不变（仍是「设定温度 + 误差范围」两个数字），换算放在 App 里：
`TMIN = TSET − 误差`，`TMAX = TSET + 误差`（`tempPresetName()` 生成的 `350±20` 仍只是显示名）。

> 若真机扫码后 `0x1B/0x1C` 没变，说明判断错了 —— 改 `QrGen.configPayload()` 一处即可退回 `TERR`
> （单测 `TempConfigQrTest` 会立刻红灯，不会静默改坏）。

### 23.2 数据模型：新增一张 `limit_preset` 表（DB v7）

两个上限字段完全相同，**不分表**，用 `kind` 区分（`LIMIT_VMAX` / `LIMIT_RMAX`）：

| 列 | 含义 |
|---|---|
| `kind` | `vmax`（漏电压上限）/ `rmax`（接地电阻上限） |
| `name` | 显示名，由 kind + 数值生成：`2 mV` / `2.5 Ω` |
| `valueRaw` | **寄存器原值**（×0.1）：`20` = 2.0 mV |

- 唯一索引 `(kind, name)` —— 同一类别内同名即同参数；带上 kind 才能让两类各有一档 `2`。
- `MIGRATION_6_7` 纯建表，不动 `measurement_record`（上限值本来就随每笔结果快照在
  `voltageLimitOhm` / `resistanceLimitOhm` 列里，历史不受影响）。
- 备份 version 3 → 4，新增 `limitPresets` 数组（只存 `kind` + `valueRaw`，名称导入时重算；
  不认识的 kind 一律丢弃）；旧备份缺这项按 0 处理，**向前兼容**。

### 23.3 二维码组装规则（用户定：选哪项配哪项）

顺序固定，与厂家表格自上而下一致：`SN` → `TSET` → `TMIN` → `TMAX` → `VMAX` → `RMAX`。
**传 null 的项整条不输出** —— 只选了漏电压上限，得到的就是 `VMAX=2`，绝不会顺手把温度也改掉。

| 测量页选中项 | 二维码内容 |
|---|---|
| 全选（编号 `QK-HT-001`、350±20、2 mV、2.5 Ω） | `SN=QK-HT-001,TSET=350,TMIN=330,TMAX=370,VMAX=2,RMAX=2.5` |
| 只选温度设置 | `TSET=350,TMIN=330,TMAX=370` |
| 只选漏电压上限 | `VMAX=2` |
| 只选设备编号 | `SN=QK-HT-001` |
| 什么都没选 | **`null` → 按钮置灰，不生成空码** |

- 按钮可用条件 = 温度 / 漏电压 / 电阻 / 设备编号**任意一项有选择**（用户原话是前三项，设备编号一并放开 ——
  厂家表 1 的单条指令示例本身就是一条 `SN=…`，只配编号是合法且常用的动作）。
- 温度三项**成组**：只有设定温度没有误差范围时算不出上下限，**宁可整组不出**（宁缺勿错配）。
- `TMIN`/`TMAX` 允许为负（设定温度小的场景），不做额外夹取 —— 仪器侧怎么处理是黑盒，不替它猜。

### 23.4 单位口径与**待实测**的一处假设

厂家示例 `VMAX=2`（表头单位 mV），而真机 `0x1D` 出厂默认原值 `20` = 2.0 mV —— 两者是 **10 倍关系**。

**现行做法（假设 A）**：二维码里发**整单位值**（`2` = 2 mV），存库按寄存器原值（×10）存。
即 `VMAX=2` ⇄ `0x1D=20`。

> 另一种可能（假设 B）：二维码里发的是**寄存器原值**本身（`VMAX=2` → `0x1D=2` = 0.2 mV）。
> **分辨方法（扫一次就知道）**：扫 `VMAX=2` 后在测量页最下方「仪器状态」看**电压上限** ——
> 显示 `2.0 mV` = 假设 A 成立（现行）；显示 `0.2 mV` = 假设 B，改 `limitValueText()` 一处即可。
> 管理页列表右侧与新增/修改对话框都已经把「扫码后仪器 `0x1D` 应变为 20」写出来了，就是为了一眼核对。

输入允许**一位小数**（`0.1 mV` / `0.1 Ω` 分辨率），因为寄存器本身就是 ×0.1。
但**厂家示例只有整数**，小数是否被仪器接受**未实测**；若仪器只认整数，界面提示不要输小数即可（App 不拦）。

### 24.3 FTDI 驱动要素（自己写驱动最容易踩的三个坑）

1. **分频编码**：16 位里 bit0..13 是整数部分、bit14..15 是小数部分（只能取 0/0.125/0.25/0.5）。
   19200 → `0x809C`，9600 → `0xC138`，38400 → `0x404E`，115200 → `0x001A`。`FtdiBaud` 纯计算、
   10 例单测逐个钉死；诊断页同时显示**实际达成的波特率**与是否精确，让人一眼看出偏差。
2. **每个 USB 包开头的 2 个 modem 状态字节必须剥掉**（一个包 = 2 状态 + 最多 62 数据）。
   不剥就会每隔 62 字节混进两个垃圾字节，行会被从中间切断 —— 这类 bug 现场极难查。
   `stripStatusBytes` 单测覆盖（含跨包残留的边界）。
3. **接口不能写死 0**：FT2232/FT4232 是双/四通道，写死接口 0 会挑到空通道。
   `open()` 遍历所有接口找带 bulk IN 端点的那个再声明。

配置全程打印**逐步执行日志**（`✔ 拉 DTR+RTS` / `✘ 波特率 …（返回 -1）`），诊断页原样显示；
「打开失败」四个字在现场没有任何用，要能看出**是哪一步**失败。

### 24.4 数据模型：两张新表（DB v8）

```sql
torque_dict    (id, kind, name, enabled, createdAt, updatedAt)   -- UNIQUE(kind, name)
torque_record  (id, snapshotKey, timestampMs, lineName, modelName, rangeName, deviceName,
                sessionId, seqInSession, isAverage, measuredValue, sampleCount,
                unitText, judgeText, rawLine, rawHex)            -- UNIQUE(snapshotKey), INDEX(timestampMs)
```

- **四类字典合一张表**（`kind` ∈ `line|model|range|device`）：它们字段完全相同，只是「一个名字」；
  与 `limit_preset` 同一个理由，分四张表只会让迁移/备份/DAO 各多写三份。
- **`snapshotKey` 唯一索引**：幂等键（与烙铁 `measurement_record` 同一套做法），
  同一笔重复入库会被 IGNORE 掉，不会因重连/重放变成两条记录。
- **`measuredValue` 可空**：解析不出数值的行**照样入库**（`rawLine`/`rawHex` 还在），
  界面上显示 `--` 并带「单位待确认」。丢原文比丢数值更糟。
- 迁移 `MIGRATION_7_8` 的 SQL 已与 ksp 生成的 `AppDatabase_Impl.java` **逐字比对**
  （两张表 16 个字段 + 3 个索引全部一致）。⚠️ 仍**未在真机上做过 7→8 的实机升级**。

### 24.5 数据隔离的落法（用户要求 1）

「独立」的实质是**读写路径互不交叉**，而不是各建一个数据库文件：

| 维度 | 烙铁 | 扭力计 |
|---|---|---|
| 表 | `measurement_record` | `torque_record` |
| DAO | `RecordDao` | `TorqueRecordDao` |

| 导出 | `XlsxExporter` → `测温记录_*.xlsx` | `TorqueXlsxExporter` → `扭力计记录_*.xlsx` |
| 界面 | `ui/measure` `ui/history` `ui/manage` `ui/diagnostic` | `ui/torque/*`（**不 import 烙铁界面任何东西**） |

**共用**的两样，都是刻意的：**同一个数据库文件**（删除密码存在 `app_setting`，

### 24.6 烙铁通信不受影响（用户最强调的一条）

结构上可核对的三点：

1. 烙铁的轮询与保存判定跑在 `MeasurementController` 自己的协程里，由 `Application` 持有；
   页面切换只改 `Page` 枚举序号，**不构造也不销毁任何控制器**。
2. `MeasureScreen` 里**没有** `LaunchedEffect` / `DisposableEffect` / `onDispose`，从不调用
   `controller.start()` 或 `stop()` —— 它只是 `collectAsStateWithLifecycle` 一个只读状态。
3. 烙铁「三次平均自动保存」的判据在 `SaveTrigger`（**控制层**，在轮询协程里跑），
   不在界面上 —— 所以哪怕正停在扭力计页，烙铁该存的照存。

> 这三条是**代码结构**上可核对的，不是真机验证结论；真机上的「切页时烙铁不断线」仍需实测（见 24.9）。

**自动切页**（用户要求）：收到扭力读数 → 切到扭力计页；收满三次平均 → 切页 + 振动 + 弹卡。
两个安全阀：①**只在烙铁测量页时**才自动切（人正待在历史/配置/管理/诊断页时不抢）；
②手动切页后 **5 秒内**不自动切（否则人刚点回烙铁页就被抢走）。扭力计的弹卡时间 8 秒（烙铁是 5 秒）。

## 25. 扭力计按实测格式定稿 + 界面修正（2026-09-22，v9）

> 本节**推翻 §24.9 的下列条目**：第 1 条「报文格式完全未知」、第 9 条「判定语未知、不判定」。
> 依据是用户 2026-09-22 用串口调试助手做的实测（截图 + 原始数据），其余条目的状态见 §25.9。

### 25.1 实测确认的事实（不再是猜测）

| 项 | 实测值 | 来源 |
|---|---|---|
| 串口参数 | **19200 / 8 数据位 / 2 停止位 / 无校验 / 无流控** | 用户串口助手配置截图 |
| 报文格式 | `+5.40kgf*cm`：**带符号十进制数 + 单位 `kgf*cm`**，2 位小数 | 用户串口助手 RX 区原文 |
| 分隔 | 设备**不发换行符**；串口助手是靠「分包间隔 50ms」把每笔切开显示 | 用户截图里每笔 50ms 一行 |
| 单位 | `kgf*cm`（星号是设备原样写法） | 同上 |

连续实测样本：`+5.40` / `+6.23` / `+3.38` / `+3.12` / `+2.94` / `+2.05`（单位均为 `kgf*cm`）。

**解析实现随之改模型**（`TorqueParser`）：从「按行切分 + 逐行抽取」改为
**扫描整段字节找 `符号+数字+单位`**，一次 `feed` 能返回 0~N 笔。原因有三条，都是真机必然发生的：

1. 不发换行 → 旧模型会把「最后一行」永远留在缓冲里，**漏掉最后一笔**；
2. 两块数据可能落在同一次 `bulkTransfer` 里（`+5.40kgf*cm+6.23kgf*cm`）→ 旧模型一整串当一笔；
3. 一笔可能被切成两个包（`+5.4` | `0kgf*cm`）→ 必须带缓冲拼接后再匹配。

认不出来的字节**不丢**：留在缓冲里，由诊断页显示「解析缓冲 N 字节 + 未识别内容 + 丢弃字节数」——
格式万一又变了，现场看到的是「缓冲堆着几十字节」，不是「数据凭空少了」。

### 25.2 数据模型 v9（一处加列 + 一处重建）

- `torque_dict` **加两列** `minValue` / `maxValue`（REAL，仅 `kind='range'` 有值）——
  用户要求 5：新增扭矩范围要填**上限 + 下限**两个数，单位 kgf*cm。
- `torque_record` **由「一笔一行 + 一行平均」改为「一组一行」**：
  第 1/2/3 笔 → `v1` / `v2` / `v3`，加 `average` / `judge` / `rangeMin` / `rangeMax` 快照
  （用户要求 4：导出必须有时间、线别、机种、扭矩范围、设备信息、**三次结果**、平均、判定）。
  SQLite 改不了列 → `MIGRATION_8_9` 重建表并按 `sessionId` 聚合：
  `MAX(CASE WHEN seqInSession=1 THEN measuredValue END)` 还原三笔、平均行还原到 `average`；
  旧数据**没有判据**（范围上下限当时不存在）→ `rangeMin/rangeMax` 留 NULL、`judge` 留空串，
  界面与导出都显示「**未判定**」—— 不编造判定。
- 烙铁的表**一个字段都没动**（这是「加新界面不能影响烙铁」在数据库层的又一次落实）。

### 25.3 判定（用户要求 6）

`平均值 ∈ [下限, 上限] → OK，否则 NG`，**闭区间**（恰好在边界上算合格，现场按标准值卡边界时
判成不合格会引起不必要的返工）。三个值缺任何一个 → 不判定（返回 null，不编造）。

**先按 2 位小数圆整、再判定**：设备输出就是 2 位，取 `5.003333…` 去比上下限会出现
「屏幕上显示 5.00、判定却按 5.003333 算」这种自相矛盾。圆整后显示值、判定值、导出值三者永远同源。

判定函数 `torqueJudge()` 是**界面、入库、导出共用的同一个纯函数** —— 两边不可能算出不同的结论。

### 25.4 一次测量的完整流程（用户 2026-09-22 定稿）

```
在扭力计上测一笔 → 进暂存组（1/3、2/3、3/3，界面三格分开显示）
   ├─ 不满 3 笔：等下一笔（暂存只在内存，库里没有半截记录）
   └─ 满 3 笔：起延时（默认 5 秒，可在诊断页改 3/5/10/15/30 秒）
        ├─ 期间点「重测」 → 清空本组三笔、取消计时，重新从 1/3 开始（无需密码）
        ├─ 期间又来一笔 → **不并入本组**，记一笔「已忽略」（页面写明 + 日志留痕），本组照常保存
        └─ 时间到：
             ├─ 四项信息（线别/机种/扭矩范围/设备信息）**全选齐** → 写一行记录
             └─ **缺任何一项 → 不保存**，页面弹橙色醒目告警并把这几个下拉整块点亮，
                组仍留在暂存里；补选后**立刻**保存（不用再等一轮）
```

保存成功后：弹全屏结果卡（底色 = 判定色，绿 OK / 红 NG）+ 振动，并**清空「设备信息」**
（它是电动螺丝机的 ID，下一件换机台）。「时间」列取**第三笔的时刻**（用户拍板）。

数据可靠性沿用烙铁那套：每组先写 `pending`（`app_setting`）→ 幂等插入（`sessionId` 唯一索引）
→ 清 pending；崩在中间由启动时的 `recoverPending()` 补记，重复由唯一索引吸收。

### 25.5 界面：切换条被系统导航栏压住（用户要求 1）—— 根因与修法

**根因**（读代码定位，非猜测）：`MainActivity` 开了 `enableEdgeToEdge()`；
`App.kt` 里内容 `Box` 用了 `systemBarsPadding()`（**含导航栏内边距**），
而底部切换条 `SwitchBar` 是这个 `Box` 的**兄弟节点、排在它下面** ——
结果导航栏的内边距被算进了「内容区」，切换条又被排到内容区之后，**正好画在系统导航栏底下**
（现场表现：太矮、被手势条挡住、点不到）。

**修法**：确立一条规矩 —— **谁在最下面，谁负责导航栏的内边距**：
- 有切换条时（两个测量页）：内容只让开状态栏（`statusBarsPadding()`），
  **切换条自己用 `navigationBarsPadding()`**（加在 Surface 内部：背景色铺到屏幕最下沿，
  可点内容整体抬到导航栏之上）；
- 没有切换条时（历史/配置/管理/诊断等子页）：内容自己让开导航栏。

同时按用户「太矮了」把切换条可点高度 **64dp → 88dp**、标题字号 20 → 24sp、状态圆点 12 → 14dp。

## 26. FTDI 8N2 配置纠错 与「数据中间乱码」的定性（2026-09-23/24，不动版本）

> 本轮只碰 USB 采集这一层：**烙铁侧（MODBUS TCP）与页面结构零改动**，数据库版本、备份格式标识都没动。

### 26.0 本轮拿到的原始材料

| 材料 | 内容 | 可读性 |
|---|---|---|

所以下面凡涉及「那天到底收到了什么字节」，一律标【未知】——**不编数据**。

### 26.1 手册确认的两条事实（推翻/确认 §24.9、§25.9 的相应条目）

1. **`19200 8N2 无校验` 是手册白纸黑字**（§24.9 第 3 条「未在真机上验证」→ 参数本身现在是**厂家文档级事实**）。
2. **输出是 ASCII**（与 §25 的实测格式一致），但手册**没说**设备只发读数、不发别的字节 ——
   这是理解「乱码」的关键前提，见 26.4。

### 26.2 【事实，已修】`SET_DATA`(0x04) 的 wValue 位域放错了：0x0208 → 0x1008

```
位域（FT232/FT245 Device API 与 libftdi 一致）：
| 0–7 数据位 | 8–10 校验(0=无 1=奇 2=偶 3=Mark 4=Space) | 11–13 停止位(0=1位 1=1.5位 2=2位) | 14 break | 15 保留 |
```

| | 值 | 实际含义 |
|---|---|---|
| 改之前 | `8 or (2 shl 8)` = **0x0208** | 8 数据位 + **偶校验** + 1 停止位 ❌ |
| 改之后 | `8 or (2 shl 11)` = **0x1008** | 8 数据位 + 2 停止位 + 无校验 ✅（= 手册） |

依据（两条独立来源，都已核对源码/文档）：
- usb-serial-for-android 的 `setParameters()`：无校验不加位、奇 `0x100`、偶 `0x200`、两位停止位 `config |= 0x1000`；
- FTDI 官方 API 文档的 wValue 位表（上表）。

**为什么错成这样还能读出数**（【推断】，但可自行验证）：设备发 8N2、芯片按 8E1 收，
两者一帧都是 11 位（1 起 + 8 数据 + 2 停 vs 1 起 + 8 数据 + 1 校验 + 1 停），
**位的采样位置完全重合** → 8 个数据位照样采对，只是设备的**第 1 个停止位**被当成偶校验位，
于是约一半字节（1 的个数为偶数的那些）会报校验错。数据位没被移动，所以读数还能认出来 ——
这也解释了为什么「解析器靠内容扫描仍能认出读数」与「数据里夹着看不懂的东西」能同时成立。

⚠️ 但必须说清：**芯片收到校验错之后在 VCP 数据流里怎么表现，本轮没有查到可靠结论**
（是照原样送出、还是替换/插入错误字节）。这条留在 26.4 里当【未知】。

### 26.3 【事实，已核源码】状态字节剥离：我们与成熟库逐句等价，且「按包长步进」只在大缓冲下才有意义

2026-09-24 取到 usb-serial-for-android 的 `FtdiSerialDriver.java` 源码（经镜像），关键三处逐字如下：

```java
private static final int READ_HEADER_LENGTH = 2;   // contains MODEM_STATUS

protected int readFilter(byte[] buffer, int totalBytesRead) throws IOException {
    final int maxPacketSize = mReadEndpoint.getMaxPacketSize();
    int destPos = 0;
    for(int srcPos = 0; srcPos < totalBytesRead; srcPos += maxPacketSize) {
        int length = Math.min(srcPos + maxPacketSize, totalBytesRead) - (srcPos + READ_HEADER_LENGTH);
        if (length < 0)
            throw new IOException("Expected at least " + READ_HEADER_LENGTH + " bytes");
        System.arraycopy(buffer, srcPos + READ_HEADER_LENGTH, buffer, destPos, length);
        destPos += length;
    }
    return destPos;
}

// 读循环里还有一条：只有状态的 2 字节包会被读掉重来
do { nread = super.read(dest, length, ...); } while (nread == READ_HEADER_LENGTH && ...);
```

结论：
1. `[stripStatusBytes]` 与它**逐句等价**（`srcPos += maxPacketSize`、每处留 2 字节头）——之前的移植是对的；
   两处**有意不同**：库里 `length < 0` 抛异常，我们选择**跳过**（现场宁可少 2 字节，也不能因一个畸形包判链路断开）。
2. 那条 `while (nread == READ_HEADER_LENGTH)` 顺带证实了「**只有状态、没有数据的 2 字节包**」真实存在。
3. ⚠️ **更正本轮之前的一个误判**：曾把「数据中间出现 `01 60`」当成乱码成因，说成「一次读装进多个包、
   只剥第一处」。本驱动的读缓冲**正好是一个包长**（`readPacket` 只请求 `packetSize` 字节），
   而 USB 短包会立刻结束一次 `bulkTransfer` → **一次读最多只装得下一个包**，
   「只剥前 2 字节」与「按包长步进」结果完全相同。步进写法**保留为保险**（缓冲一旦加大就必须步进），
   但**它不是乱码的原因** —— 代码注释与测试名字都已按这个口径改正，免得下一个人再往这儿找。

### 26.4 「数据中间有很多乱码」的三种可能（【未知】，但有可判读的指纹）

| 可能 | 机理 | 在诊断页长什么样 | 现在的判据 |
|---|---|---|---|
| A. **数据位配置错（26.2）** | 8E1 收 8N2 → 校验错，芯片对错误字节的处理方式未定 | 状态头第 2 字节在几种值之间跳；`未识别` 缓冲里堆着**散乱**的高位字节 | 已修 8N2，下一轮直连看是否消失 |
| B. **设备本身还发别的字节**（手册只保证读数用 ASCII，没说不发别的） | 例如发一串设备信息/状态文字 | `未识别` 缓冲里每次都是**同一段稳定字节**；若是合法 UTF-8 文字 → 新增的「按 UTF-8 看」一行会把它显示成正常文字 | 诊断页新增判读（26.5） |
| C. **界面观感**：那 2 个状态头字节本来就不是数据 | FTDI 每包固定 2 字节头（实测 `01 60`） | 「含状态字节」视图里每帧都以 `01 60` 开头，看着像乱码 | 诊断页新增状态头统计 + 位含义解码（26.5） |

**今天无法在三种之间定案**（截图分辨率不够，见 26.0），所以本轮**不猜**：
把能修的（A 的配置）修掉，把能判读的（B/C 的显示）补上，剩下交给下一次真机。

### 26.5 诊断页三处增强（只读，不碰采集逻辑）

1. **状态头统计**：从留存的帧里数出各状态头的出现次数并解出线路状态位，
   例如 `01 60 ×37（DSR+RI）`。位值取自 libftdi / usb-serial-for-android 的
   `MODEM_STATUS_*`（`0x10=CTS 0x20=DSR 0x40=RI 0x80=CD`），实测设备稳定报 `01 60`。
   **全都一样 → 链路安静；出现好几种 → 芯片在报线路状态变化**（这时才该怀疑 A）。
2. **「按 UTF-8 看」**：把 `未识别` 那段字节**严格按 UTF-8** 再解一次，能解出非 ASCII 文字就显示出来。
   用到 `CodingErrorAction.REPORT`：Java 的 `String(bytes, UTF_8)` 会把非法字节悄悄换成 U+FFFD，
   那样「解出来有字」就没有证据价值 —— 必须解不通就返回 null（有单测）。
3. 底部提示改写：明确写出「第 1 字节固定 01、第 2 字节是线路状态位」，
   并说清「看到 `01 6x` 混在中间先看含/已剥对照列，不要当成乱码」。

### 26.6 第三方提案的复核结论（逐条）

| 提案 | 结论 | 理由 |

## 27. 协议字符白名单（读取层滤噪声）（2026-09-25，不动版本）

### 27.0 用户输入（原话）

> 「你这次的代码已经快接近正确答案了，但是中间会出现 `\x18 \x0E \x0F` 这些没用的数据，**你不需要保留原始数据流**：
> 你只关心 `+ 5.40 kgf*cm` 这样的读数，其他东西全是噪声。」
> 「**白名单过滤方案**：读取层只保留协议允许的字符，其余全部丢弃。剩下的干净数据交给解析器按 `\r\n` 切分 + 正则匹配。」

提案代码要点：放行 `0-9` `A-Z` `a-z` `+` `-` `.` `*` 空格 `\r` `\n`，其余全部丢掉。

### 27.1 采纳的部分

| 项 | 处置 |
|---|---|
| **读取层白名单过滤** | **采纳**（本方案主体）。`TorqueStreamParser.keepProtocol()` 在**读循环**里应用，送进解析器的字节只可能是 `+ 5.40 kgf*cm` 这类字符 |
| 过滤掉多少字节 | **如实计数**：每帧 `TorqueFrame.noiseBytes` + 累计 `TorqueUiState.noiseTotal`，诊断页显示 —— 保住「不静默丢数据」这条纪律 |
| 诊断页文字那一行 | 改成显示**过滤后**的内容（现场看到的就是读数），另加「（滤除 N 字节）」标注 |
| 白名单额外放行 `·`（0xB7） | **采纳前补的一个字节**：单位变体里有 `kgf·cm`（§25 的 `UNIT_EXPR`），滤掉它会让一种本来认得的写法突然失配。附带好处：设备若发 UTF-8 的 `·`（`C2 B7`），`C2` 被滤、`B7` 留下，反而认得出来 |

**为什么这个方案确实修好了现场那件事**（有单测对照，见 27.4）：

### 27.2 没有采纳的部分（及其理由）

| 提案 | 结论 | 理由 |
|---|---|---|
| 「剩下的干净数据交给解析器**按 `\r\n` 切分**」 | **不采纳，仍用内容扫描** | 设备**不发换行符**是本项目 2026-09-22 的实测结论（串口助手按 ~50 ms 分包显示，报文之间没有 `\r\n`，§25）。按行切分的**前提**恰恰是「每笔都以 CRLF 结尾」，前提不成立时每一笔都会卡在缓冲里**一笔都出不来**——这是可靠性上的倒退。现有扫描式解析对「有没有 CRLF」**两种情况都对**：真发了 CRLF 也只是被当空白跳过。**CR/LF 已放进白名单**，所以「发 CRLF 也不丢字节」这一点是成立的；哪天真机 hex 里确认了 `0D 0A`，改成「以 CRLF 为额外边界提示、但保留扫描兜底」只是一行的事 |
| 「**不需要保留原始数据流**」 | **部分采纳** | 采纳的是**解析路径**：噪声不再进入解析缓冲（诊断页「未识别」那行列出的就是真正卡住的字符，不会再躺着 `\x18 0E 0F`）。**保留**的是每帧的「滤噪声之前」逐字节 hex（`dataHex`）与状态头统计 —— 这两样是**回看设备到底发了什么**的唯一凭据，删掉之后「噪声是链路采样产生的还是设备本身在发非协议内容」这个问题就永远查不清了。保留成本为零（只是一段字符串，帧数上限 200），且界面正行已经是干净读数，现场不会看到它 |

### 27.3 事实 / 推断 / 未知

- 【事实】`\x18 \x0E \x0F` 这类字节**确实出现在用户现场的数据流里**（2026-09-25 用户反馈，2026-09-24 的诊断截图同样有橙色未识别行）。
- 【事实】这些字节**不可能出现在读数里**：协议读数是 `+`/`-`、数字、`.`、空格、单位字母、`*`。
- 【事实】噪声**夹在读数中间**会让整笔读数认不出来：`+ 5.40 k\x18\x0E\x0Fgf*cm` 在不过滤时正则匹配不到 `kgf`，整笔丢掉并堆在缓冲里（已写成单测对照）。**所以白名单不只是「界面干净」，它实际救回了被切碎的读数。**
- 【推断】滤掉这些字节**不会**改变读数字节：白名单是「字符集判断」，对读数里合法出现的字符一个都不动。
- 【未知】**这些字节从哪来**仍然未定案：可能是链路采样产生的坏字节，也可能是设备本身在发非协议内容（§26.4 的可能 B【设备发文字】/C【状态字节残留】仍在）。现在无法从读数这一侧区分 —— 只能看诊断页「滤掉的字节按 UTF-8 看」那一行（能解成正常文字 = 设备在发文字；解不出来 = 更像链路坏字节）。
- 【已知残余风险 1】白名单**无法发现「数字本身被采坏」**：若某个数字位被采成了另一个白名单内的字符，会得到一笔**看起来正常但是错的读数**。这是本方案的固有代价（原方案同样发现不了，只能靠比对设备屏幕）。
- 【已知残余风险 2】把噪声**当成不存在**在极端情况下会把两段碎读数接成一笔。当前协议每笔都带单位、数字位数固定（2 位小数），接错的概率低，但没有数学上的排除。

### 27.4 单测对照（为什么说它「救回了被切碎的读数」）

```kotlin
val wire = "+ 5.40 k" + byteArrayOf(0x18, 0x0E, 0x0F) + "gf*cm"
TorqueStreamParser().feed(wire).size          // 0 笔 —— 单位被切碎，整笔丢，还堆在缓冲里
TorqueStreamParser().feed(keepProtocol(wire)) // 1 笔 = 5.40，缓冲 0 字节
```

### 27.5 顺带修掉的一处判读口径

「严格 UTF-8 判读」（§26.5 加的仪器）原先挂在**解析缓冲**上；缓冲现在只可能装白名单字符（ASCII + `·`），那个位置就永远解不出东西了。因此把它**重新指向被滤掉的那些字节**：

- `droppedTextOrNull(raw)`：把被滤掉的字节严格按 UTF-8 试解，解成**含非 ASCII 的文字**才返回（诊断页显示「滤掉的字节按 UTF-8 看：…」），用途不变 —— 区分「设备在发文字」和「链路坏字节」。
- 【顺带修正】`hasNonAscii` 的界从 `> 0x7E` 改成 `> 0x7F`：`0x7F`(DEL)、`0x01` 这类控制字符**正是链路噪声的常见样子**，把它们算成「设备在发文字」会把排查方向带偏（新增单测钉住）。ASCII 的定义本来就是 `0x00–0x7F`。
